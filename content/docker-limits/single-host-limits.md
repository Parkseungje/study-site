PART 1 부터 여기까지 **한 대의 호스트**를 전제했다.

```
Compose 는 한 호스트 안에서만 동작한다       (compose-basics)
볼륨은 한 호스트에 묶인다                     (volume-backup)
bridge 네트워크는 한 호스트 안이다            (network-drivers)
unhealthy 를 Docker 는 기록만 한다            (healthcheck)
depends_on 은 시작할 때 한 번만 평가된다      (startup-order)
```

전부 **"그래서 오케스트레이터가 필요하다"**로 끝났다.
이제 그 말이 무슨 뜻인지 정리한다.

출발점은 한 문장이다. **그 서버가 죽으면 전부 죽는다.**

## 0. 들어가기 전에 — 핵심 용어

- **단일 장애점(SPOF)**: 그것 하나가 죽으면 전체가 멈추는 지점.
- **수직 확장(scale up)**: 서버 사양을 올리는 것.
- **수평 확장(scale out)**: 서버 대수를 늘리는 것.
- **오케스트레이션**: 여러 호스트 위에서 컨테이너를 **배치·감시·교체**하는 일.
- **무중단 배포**: 서비스를 끊지 않고 새 버전으로 바꾸는 것.
- **서비스 디스커버리**: 어느 호스트에 무엇이 떠 있는지 찾는 것.

한 줄 그림: **컨테이너는 "어떻게 실행할까"를 풀었고, 오케스트레이터는 "어디에 몇 개를 띄울까"를 푼다.**

비유하자면 **요리사 한 명과 주방 운영**이다.
지금까지 배운 것은 **요리법**이다. 재료를 손질하고 조리하는 법.
그런데 **손님이 200명**이 되면 다른 문제가 생긴다.
요리사를 몇 명 둘지, 한 명이 아프면 누가 대신할지,
주문이 몰리면 어떻게 늘릴지. **요리법으로는 못 푸는 문제**다.

## 1. 그전엔 어떻게 했나 — 한 대로 버티기

### 고통 1 — 서버가 죽으면 전부 멈춘다

```bash file=terminal
$ ssh prod-01
ssh: connect to host prod-01 port 22: No route to host
```

디스크가 고장났다. 커널이 패닉했다. 데이터센터 전원이 나갔다.

**그 서버의 모든 컨테이너가 같이 죽는다.**
`restart: unless-stopped` 도 소용없다. 호스트가 없으니까.

그리고 **복구가 수동**이다. 새 서버를 띄우고, Docker 를 깔고,
저장소를 받고, 볼륨을 복원하고([[volume-backup]]), 띄운다.
그 사이 **서비스가 멈춰 있다.**

### 고통 2 — 부하가 늘면 사양을 올리는 수밖에 없다

```
트래픽 2배 → CPU 가 모자라다
→ 서버를 더 큰 것으로 교체한다 (수직 확장)
→ 교체하려면 멈춰야 한다
→ 그리고 언젠가 가장 큰 서버로도 모자란다
```

`docker compose up --scale app=4` 로 늘릴 수는 있다.
그런데 **같은 호스트 안**이다. 그 호스트의 CPU 와 메모리를 나눠 쓸 뿐이다.

**호스트 하나의 사양이 천장**이고, 그 천장은 비싸게 올라간다.

### 고통 3 — 배포할 때 끊긴다

```bash file=terminal
$ docker compose up -d
[+] Running 1/1
 ✔ Container myapp-app-1  Recreated
```

[[compose-basics]] 에서 본 것이다. **지우고 다시 만든다.**
그 사이 요청이 **거부된다.**

컨테이너를 여러 개 띄워도 마찬가지다. Compose 는
**하나씩 교체하면서 트래픽을 빼주지** 않는다.

`--scale` 로 늘려두고 수동으로 하나씩 바꾸는 흉내를 낼 수 있는데,
**로드 밸런서가 그 상태를 알아야** 한다. 그걸 연동할 수단이 없다.

### 고통 4 — 어느 서버에 떠 있는지 모른다

서버를 두 대로 늘렸다고 하자.

```
prod-01 : app, db
prod-02 : app
```

`app` 이 `db` 를 부르려면 어떻게 하나.
[[container-dns]] 의 서비스 이름은 **같은 호스트의 같은 네트워크**에서만 풀린다.

```yaml file=compose.yaml bad label="IP 대장으로 돌아간다"
environment:
  DB_HOST: 10.0.1.23
```

[[container-dns]] 의 고통 1 그대로다. 서버가 교체되면 IP 가 바뀌고
**전부 고쳐야 한다.** 그리고 어느 서버가 살아 있는지도 모른다.

### 고통 5 — 설정과 비밀을 서버마다 복사한다

```bash file=terminal
$ scp .env prod-01:/srv/app/
$ scp .env prod-02:/srv/app/
$ scp secrets/db_pw prod-01:/srv/app/secrets/
# ... 서버가 늘 때마다
```

[[secrets]] 에서 "파일이 복사되며 퍼진다"고 한 것이 **서버 단위로** 일어난다.
한 서버만 빠뜨리면 그 서버의 앱이 다르게 동작한다.
그리고 비밀을 **회전**하려면 전부 다시 돌아야 한다.

다섯 고통의 뿌리는 **하나**다. **Docker 는 호스트 하나를 다룬다.**
호스트 **사이**의 일을 다루는 층이 없다.

## 2. 이렇게 피해봤다

### 시도 1 — 서버를 크게 쓴다

고통 2 의 대응이다. **단순하고 실제로 꽤 멀리 간다.**

요즘 서버는 코어 128개에 메모리 1TB 도 있다.
많은 서비스가 **한 대로 충분하다.**

**고통 1 이 그대로 남는다.** 큰 서버도 죽는다.
그리고 **죽으면 더 크게 아프다.** 거기에 전부 들어 있으니까.

### 시도 2 — 서버 두 대를 두고 수동으로 나눈다

```
prod-01 : app, db
prod-02 : app
앞에 nginx 로 로드 밸런싱
```

**고통 1 이 부분적으로 완화된다.** `prod-02` 가 죽어도 `prod-01` 이 산다.

그런데 **`db` 가 있는 `prod-01` 이 죽으면 전부 멈춘다.**
그리고 고통 4 와 5 가 생긴다. IP 를 관리하고 설정을 복사해야 한다.

**서버가 세 대, 네 대가 되면 사람이 못 따라간다.**

### 시도 3 — 배포 스크립트를 정교하게 만든다

```bash file=deploy.sh
for host in prod-01 prod-02; do
  ssh $host 'docker compose pull && docker compose up -d'
  sleep 30
  curl -f http://$host/health || exit 1
done
```

**무중단 배포를 흉내낸다.** 실제로 많이 쓰이는 방식이다.

그런데 직접 처리해야 할 것이 끝없이 늘어난다.

```
로드 밸런서에서 빼고 넣기
헬스체크가 통과할 때까지 기다리기
실패하면 롤백하기
동시에 몇 대까지 교체할지
배포 중 다른 사람이 배포하는 것 막기
```

**스크립트가 작은 오케스트레이터**가 되어간다.
그리고 그 스크립트는 **테스트되지 않는다.**

### 시도 4 — 클라우드의 관리형 컨테이너 서비스를 쓴다

ECS, Cloud Run, App Runner 같은 것들이다.

**좋은 선택이고 실제로 많이 쓴다.** 오케스트레이션을 클라우드가 해준다.

다만 **그 클라우드에 묶인다.** 그리고 결국
"어디에 몇 개를 띄울까"를 **설정으로 표현해야** 하므로,
이 글에서 보는 개념들이 그대로 필요하다.

> 네 시도의 공통점: **호스트 사이의 일을 사람이나 스크립트가 했다.**
> 그것을 **전담하는 층**이 오케스트레이터다.

## 3. 그래서 나온 것 — 호스트 위에 층을 하나 더

```
컨테이너      : 한 호스트에서 "어떻게 실행할까"
오케스트레이터 : 여러 호스트에서 "어디에 몇 개를 띄울까"
```

다섯 고통과 대응시켜 보자.

| 고통 | 필요한 것 | 오케스트레이터가 하는 일 |
| --- | --- | --- |
| 서버가 죽으면 전부 멈춘다 | 분산 배치 | 노드 장애를 감지하고 **다른 노드에 다시 띄운다** |
| 사양을 올리는 수밖에 없다 | 자동 확장 | 부하를 보고 **개수를 늘린다** |
| 배포할 때 끊긴다 | 롤링 업데이트 | 하나씩 교체하고 **트래픽을 자동으로 뺀다** |
| 어디 떠 있는지 모른다 | 서비스 디스커버리 | 이름으로 부르면 **살아 있는 것으로 보낸다** |
| 설정을 복사한다 | 중앙 설정 저장소 | ConfigMap·Secret 을 **필요한 노드에 전달** |

**"원하는 상태를 적으면 그 상태로 맞춘다"**가 공통 원리다.
[[compose-basics]] 의 선언형이 **호스트 여러 대로 확장된 것**이다.

```
Compose : 이 호스트에 이 컨테이너들이 있어야 한다
K8s     : 이 클러스터에 app 이 3개 떠 있어야 한다
          → 노드가 죽어 2개가 됐다 → 다른 노드에 1개를 띄운다
```

## 4. 어떻게 동작하나 — 무엇이 추가되나

```visual
id: single-host-limits-what-orchestrator-adds
kind: structure
title: 오케스트레이터가 다루는 다섯 가지
nodes:
  - name: 호스트 사이의 일
    detail: Docker 는 호스트 하나 안을 다룬다. 호스트가 여럿이 되는 순간 그 사이를 다룰 주체가 필요해지고, 그 일이 다섯 가지다
    code: Docker 가 안 다루는 영역
    children:
      - name: 배치 — 어느 노드에 띄울까
        detail: 자원이 남는 노드를 고르고, 같은 서비스를 여러 노드에 흩고, 특정 노드에만 띄워야 하는 것을 구분한다
        code: 스케줄러
        children:
          - name: 노드가 죽으면
            detail: 감지하고 다른 노드에 다시 띄운다. 고통 1 의 수동 복구가 자동이 된다
            code: 자동 재배치
          - name: Docker 로는
            detail: restart 정책은 같은 호스트에서만 동작한다. 호스트가 없으면 아무 일도 안 일어난다
            code: 호스트가 죽으면 끝
      - name: 확장 — 몇 개를 띄울까
        detail: 원하는 개수를 선언하면 그만큼 유지한다. 부하를 보고 개수를 조절할 수도 있다
        code: 레플리카 수
        children:
          - name: 수평 확장이 가능해진다
            detail: 호스트 하나의 천장이 아니라 클러스터 전체가 용량이 된다. 고통 2 의 해결이다
            code: 노드를 더하면 용량이 는다
      - name: 교체 — 어떻게 바꿀까
        detail: 하나씩 새 버전으로 바꾸면서 트래픽을 빼고 넣는다. 실패하면 멈추거나 되돌린다
        code: 롤링 업데이트
        children:
          - name: 헬스체크가 여기서 쓰인다
            detail: healthcheck 에서 unhealthy 를 Docker 가 기록만 한다고 했다. 그 신호를 실제로 쓰는 것이 이 층이다
            code: readinessProbe 로 트래픽 판단
          - name: Docker 로는
            detail: Recreated 로 지우고 다시 만든다. 그 사이가 다운타임이고 트래픽 제어 수단이 없다
            code: 끊긴다
      - name: 발견 — 어디 있는지 어떻게 아나
        detail: 이름으로 부르면 살아 있는 인스턴스로 보낸다. 컨테이너가 다른 노드로 옮겨가도 이름은 그대로다
        code: 서비스 디스커버리
        children:
          - name: container-dns 의 확장
            detail: 사용자 정의 네트워크의 내장 DNS 가 한 호스트 안에서 하던 일을 클러스터 전체로 넓힌 것이다
            code: 클러스터 DNS
          - name: 네트워크가 호스트를 넘어야 한다
            detail: network-drivers 에서 본 overlay 가 여기서 필요해진다. 그래서 overlay 를 오케스트레이터가 관리한다
            code: overlay 네트워크
      - name: 설정 — 어떻게 전달할까
        detail: 설정과 비밀을 중앙에 두고 필요한 노드에 전달한다. 서버마다 scp 하는 일이 사라진다
        code: ConfigMap · Secret
        children:
          - name: secrets 의 원칙이 그대로다
            detail: 값이 아니라 경로를 넘기고 볼륨으로 마운트한다. 다루는 범위만 클러스터로 넓어진다
            code: 파일로 마운트
```

### 그런데 지금 필요한가

**이 글에서 가장 중요한 질문**이다.

```visual
id: single-host-limits-do-i-need-it
kind: playground
title: 지금 오케스트레이션이 필요한가
inputs:
  - { name: 상황, label: 내 상황, options: [개인 프로젝트, 사내 도구, 중단되면 곤란한 서비스, 트래픽이 크게 변동, 팀에 운영 인력이 없다] }
  - { name: 요구, label: 요구사항, options: [무중단 배포, 서버 장애 자동 복구, 자동 확장, 특별히 없다] }
outcomes:
  - when: { 상황: 개인 프로젝트, 요구: 특별히 없다 }
    result: Compose 로 충분하다. 쿠버네티스를 배우려는 목적이 아니라면 복잡도만 사는 것이다
    note: 재시작 정책과 헬스체크와 백업을 갖춘 Compose 는 생각보다 멀리 간다. 필요해지기 전에 옮기지 않는다
  - when: { 상황: 사내 도구, 요구: 특별히 없다 }
    result: Compose 가 맞다. 몇 분 중단이 허용되는 서비스에 오케스트레이터는 과하다
    note: 사내 도구는 대개 야간에 아무도 안 쓴다. 그 시간에 재배포하면 무중단이 필요 없다
  - when: { 상황: 중단되면 곤란한 서비스, 요구: 서버 장애 자동 복구 }
    result: 필요하다. 한 대로는 구조적으로 불가능하다
    note: 고통 1 은 Compose 로 풀 방법이 없다. 호스트가 죽으면 그 안의 어떤 설정도 작동하지 않는다
  - when: { 상황: 트래픽이 크게 변동, 요구: 자동 확장 }
    result: 필요하다. 또는 관리형 서버리스 컨테이너를 검토한다
    note: Cloud Run 이나 Fargate 는 클러스터 관리 없이 확장만 얻는 선택지다. 쿠버네티스가 유일한 답이 아니다
  - when: { 요구: 무중단 배포, 상황: 사내 도구 }
    result: 스크립트로 흉내낼 수 있다. 다만 그 스크립트가 복잡해지는 지점을 지켜본다
    note: 시도 3 이다. 로드 밸런서 연동과 롤백까지 넣기 시작하면 작은 오케스트레이터를 직접 만드는 중이다
  - when: { 상황: 팀에 운영 인력이 없다 }
    result: 관리형을 쓴다. 쿠버네티스를 직접 운영하는 비용이 얻는 것보다 클 수 있다
    note: 클러스터 업그레이드, 인증서 갱신, 네트워크 디버깅은 전담 지식이 필요하다. EKS GKE 나 Cloud Run 이 현실적이다
  - when: { 요구: 서버 장애 자동 복구 }
    result: 노드가 최소 둘 이상 필요하다. 그것이 오케스트레이션의 최소 전제다
    note: 노드 한 대짜리 쿠버네티스는 고통 1 을 전혀 안 풀어준다. 복잡도만 얻는다
```

**"필요해지기 전에 복잡도를 사지 않는다"**가 핵심이다.

쿠버네티스는 **그 자체가 운영 대상**이다.
클러스터 업그레이드, 인증서 갱신, 네트워크 플러그인 디버깅,
리소스 요청 조정. 이 전부가 **새로 생기는 일**이다.

```
Compose 로 충분한데 K8s 로 가면 → 복잡도만 얻는다
K8s 가 필요한데 Compose 로 버티면 → 스크립트가 오케스트레이터가 되어간다
```

**두 실수가 다 흔하고**, 전자가 더 흔하다.

### 중간 선택지들

둘 중 하나가 아니다.

```
Compose              한 호스트. 가장 단순
Compose + 스크립트    한 호스트 + 수동 다중화. 흔한 현실
Docker Swarm         여러 호스트. Compose 문법과 비슷하고 가볍다
관리형 (Cloud Run 등) 확장만 얻고 클러스터는 안 본다
관리형 K8s (EKS 등)   전부 얻고 클러스터는 클라우드가 본다
직접 운영 K8s         전부 얻고 전부 책임진다
```

**Swarm 이 저평가되어 있다.** Compose 파일과 거의 같은 문법으로
여러 호스트, 롤링 업데이트, 시크릿, overlay 네트워크를 얻는다.
노드 몇 대 규모에서는 합리적인 선택이다.

다만 **생태계와 채용 시장이 쿠버네티스로 쏠려 있어서**
장기적으로는 그쪽을 보게 된다.

옮길 시점이 언제인지는 **고통이 실제로 나타나는 순서**로 가늠할 수 있다.

```visual
id: single-host-limits-when-to-move
kind: step
title: 규모가 커지며 고통이 나타나는 순서
steps:
  - name: 컨테이너 몇 개 · 한 대
    detail: Compose 로 완전히 충분하다. 오케스트레이션의 이득이 하나도 체감되지 않고 복잡도만 늘어난다
    code: Compose · 고민할 것 없음
  - name: 배포할 때 잠깐 끊긴다 — 첫 번째 고통
    detail: 보통 여기가 처음이다. 그런데 몇 초 중단이 허용되면 아직 옮길 이유가 아니다. 야간 배포로 넘어가는 경우가 많다
    code: 허용되면 아직 아니다
  - name: 끊기면 안 되게 됐다 — 스크립트가 자란다
    detail: 컨테이너를 둘 띄우고 하나씩 교체하는 스크립트를 쓴다. 로드 밸런서 연동과 헬스체크 대기와 롤백이 붙기 시작한다
    code: 시도 3 의 지점
  - name: 서버 한 대로 용량이 모자란다 — 두 번째 고통
    detail: 수직 확장으로 버틸 수 있는 동안은 버틴다. 요즘 서버는 생각보다 크다. 여기서도 아직 안 옮기는 경우가 많다
    code: 더 큰 서버로
  - name: 서버가 둘이 됐다 — 고통 4 와 5 가 한꺼번에
    detail: IP 를 관리하고 설정을 복사하기 시작한다. 두 대까지는 사람이 한다. 세 대부터 실수가 나온다
    code: IP 대장과 scp
  - name: 중단되면 곤란해졌다 — 고통 1 이 결정적이 된다
    detail: 노드 장애 자동 복구는 Compose 로 풀 방법이 없다. 여기가 구조적으로 넘어가야 하는 지점이다
    code: 구조적 한계
  - name: 그래서 판단 기준
    detail: 고통 3 은 스크립트로, 고통 2 는 큰 서버로 버틸 수 있다. 고통 1 만은 못 버틴다. 그것이 실제로 아픈지가 기준이다
    code: 고통 1 이 아프면 그때
  - name: 중간 선택지를 먼저 본다
    detail: Swarm 이나 관리형 서버리스가 쿠버네티스보다 적은 비용으로 같은 고통을 풀어주는 경우가 많다
    code: K8s 가 유일한 답은 아니다
```

## 5. 이것도 끝이 아니다 — 지금까지 배운 것이 어디로 가나

오케스트레이터가 필요한 이유를 봤다.
그러면 **지금까지 배운 것이 쓸모없어지나.**

반대다. **거의 전부 그대로 쓰인다.**

```
Pod 안의 컨테이너가 localhost 로 통신한다   → namespaces 의 그 공유
resources.limits                           → cgroups 의 그 한도
livenessProbe · readinessProbe             → healthcheck 의 그 구분
securityContext                            → PART 9 의 그 옵션들
이미지와 레지스트리                          → 그대로
```

[[kubernetes-dockershim]] 에서 본 CRI 도 여기서 의미가 생긴다.
쿠버네티스가 런타임과 대화하는 그 규격이,
**지금 배운 것 위에 오케스트레이터가 올라앉는 접점**이다.

**컨테이너를 모르면 쿠버네티스도 모른다.**
Pod 이 왜 그렇게 생겼는지, `limits` 를 넘으면 왜 죽는지,
`readinessProbe` 가 왜 따로 있는지 — 전부 PART 1~12 의 내용이다.

무엇이 어디로 이어지는지 [[next-steps]] 에서 정리한다.
Docker 커리큘럼의 마지막이다.

## 덧 — 흔한 오해

### "컨테이너를 쓰면 쿠버네티스를 써야 한다"

**별개다.** 컨테이너는 **패키징과 실행** 방식이고,
쿠버네티스는 **여러 호스트 운영** 도구다.

```
컨테이너만 쓴다          : 재현 가능한 실행 환경을 얻는다
+ Compose               : 여러 컨테이너를 선언으로 묶는다
+ 오케스트레이터          : 여러 호스트로 넓힌다
```

**앞의 둘만으로 끝나는 서비스가 아주 많다.**
그리고 PART 1 에서 본 "내 PC 에선 되는데"의 해결은
**첫 단계에서 이미 끝났다.** 그 뒤는 다른 문제를 푸는 것이다.

### "Compose 는 개발용이라 운영에 못 쓴다"

[[compose-basics]] 의 덧에서 본 것이다. **단일 호스트 운영에는 쓴다.**

```
쓸 수 있는 조건
├─ 몇 분의 중단이 허용된다
├─ 한 대의 사양으로 충분하다
├─ 백업과 복구 절차가 있다
└─ 재시작 정책과 헬스체크가 걸려 있다
```

이 조건에 맞는 서비스가 **생각보다 많다.**
사내 도구, 작은 SaaS, 블로그, 내부 API.

조건에 안 맞게 되는 순간이 **옮길 시점**이고,
그 순간을 알아보는 것이 이 글의 목적이다.

### "오케스트레이터를 쓰면 장애가 없어진다"

**장애의 종류가 바뀐다.**

```
없어지는 것 : 노드 한 대 장애, 수동 재배포 실수, 용량 부족
새로 생기는 것 : 컨트롤 플레인 장애, 네트워크 플러그인 문제,
                리소스 요청 설정 오류, 클러스터 업그레이드 사고,
                etcd 장애
```

그리고 **새 장애는 더 어렵다.** 범위가 넓고 원인이 여러 층에 걸쳐 있다.

쿠버네티스는 **가용성을 공짜로 주지 않는다.**
운영 역량과 맞바꾸는 것이고, 그 역량이 없으면
**한 대짜리 Compose 보다 가용성이 떨어질 수도** 있다.
