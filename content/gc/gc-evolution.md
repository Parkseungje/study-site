[[generations]] 끝에서 남은 문제다.

```
힙 2GB   → Full GC 수백 ms
힙 32GB  → Full GC 수 초
힙 128GB → Full GC 수십 초
```

세대 분리가 Young 의 문제는 풀었지만 **Old 의 문제는 미뤘을 뿐**이다.
그리고 요즘 서버는 힙이 수십 GB 다.

GC 종류가 여러 개인 이유가 여기 있다. **전부 같은 질문의 답**이다.

> **멈추지 않고 어떻게 수집할까.**

그리고 [[generations]] 의 시도 3 에서 접어둔 문제 —
"동시에 돌리면 살아있는 객체를 회수할 수 있다" — 를 **실제로 푼** 방법들이다.

## 0. 들어가기 전에 — 핵심 용어

- **처리량(throughput)**: 전체 시간 중 애플리케이션이 일한 비율.
- **지연(latency)**: 한 번의 멈춤이 얼마나 긴가. **p99 가 여기서 나온다.**
- **동시(concurrent)**: 애플리케이션과 **같이** 돌아가는 GC 단계.
- **병렬(parallel)**: GC 를 **여러 스레드로** 나눠 하는 것. 동시와 다르다.
- **리전(Region)**: 힙을 같은 크기로 쪼갠 조각. G1 과 ZGC 가 쓴다.
- **쓰기/읽기 배리어**: 참조를 쓰거나 읽을 때 삽입되는 추가 코드.

한 줄 그림: **처리량과 지연은 교환 관계고, GC 의 역사는 지연을 사기 위해 처리량을 파는 과정이다.**

비유하자면 **도로 공사 방식**이다.
**전면 통제**하고 한 번에 끝내면 공사는 빠르다. 대신 그동안 못 지나간다(Serial).
**인원을 늘려** 통제 시간을 줄인다. 여전히 통제는 한다(Parallel).
**차선 하나씩** 막고 차가 지나가게 하면 안 멈춘다. 대신 공사가 오래 걸리고
**지나가는 차를 관리하는 인력**이 추가로 든다(동시 GC).

도로가 넓어질수록 전면 통제의 비용이 커진다. 그래서 차선제로 간 것이다.

## 1. 그전엔 어떻게 했나 — 전부 멈추고 치운다

### Serial GC — 한 스레드가 전부 한다

```
애플리케이션 ████████──멈춤────████████──멈춤────████
GC                     █              █
                    (1 스레드)
```

**단순하고 오버헤드가 없다.** 작은 힙에서는 지금도 가장 효율적이다.

#### 고통 1 — 코어가 남는데 한 스레드만 쓴다

```
8코어 서버에서 GC 중
→ 1개 코어가 GC 를 한다
→ 7개가 논다
→ 멈춤이 8배 길다
```

**있는 자원을 안 쓴다.** 2000년대에 멀티코어가 보급되면서
이것이 분명한 낭비가 됐다.

### Parallel GC — 여러 스레드로 나눈다

```
애플리케이션 ████████──멈춤──████████──멈춤──████
GC                  ████           ████
                 (N 스레드 동시에)
```

Java 8 의 기본값이었다. 고통 1 이 풀린다.

#### 고통 2 — 여전히 전면 통제다

멈춤이 **짧아졌을 뿐 없어지지 않았다.**

```
힙 1GB,  8스레드 → STW 100ms
힙 32GB, 8스레드 → STW 3초
```

코어를 두 배로 늘려도 멈춤이 절반이 안 된다.
**작업 분배와 동기화 비용**이 있고, 힙 크기에 비례하는 부분은 남는다.

#### 고통 3 — 멈춤 시간을 예측할 수 없다

```
언제 Full GC 가 날지 모른다
그때 몇 초 멈출지 모른다
```

SLA 를 못 세운다. "99% 요청이 100ms 안에"를 약속할 수 없다.
**GC 가 돌면 그 약속이 깨지고**, 언제 돌지 모른다.

#### 고통 4 — 처리량은 좋은데 꼬리가 나쁘다

```
평균 응답 20ms
p50 18ms
p99 2,400ms      ← GC 가 걸린 요청
```

**평균만 보면 괜찮다.** 그런데 100명 중 1명이 2.4초를 기다린다.
그리고 요청이 많으면 그 1%가 **절대 수로는 많다.**

로드 밸런서가 헬스체크 타임아웃으로 판단해 **노드를 빼버리는** 일도 생긴다.
GC 한 번이 **장애로 번진다.**

네 고통의 뿌리는 **하나**다. **멈춤 시간이 힙 크기에 비례한다.**
그리고 힙은 계속 커지고 있었다.

## 2. 이렇게 피해봤다

### 시도 1 — 힙을 작게 유지한다

고통의 원인이 힙 크기면 안 키운다.

**실제로 쓰이던 전략**이다. 그리고 지금도 유효한 경우가 있다.

그런데 **메모리가 남는데 못 쓴다.** 그리고 캐시를 못 키우니
DB 를 더 때리게 되어 **전체 성능이 나빠질 수 있다.**

### 시도 2 — JVM 을 여러 개 띄운다

큰 힙 하나 대신 **작은 힙 여러 개**를 띄운다.

```
32GB 서버 → 4GB JVM 8개
```

**각 JVM 의 GC 멈춤이 짧다.** 그리고 하나가 멈춰도 나머지가 처리한다.

**관리가 늘어난다.** 그리고 **메모리가 중복된다.**
JVM 마다 Metaspace 와 코드 캐시와 스레드 스택을 따로 쓴다.
캐시도 중복돼서 전체 효율이 떨어진다.

### 시도 3 — 애플리케이션 트래픽을 빼고 GC 한다

```
노드를 로드 밸런서에서 빼고 → System.gc() → 다시 넣는다
```

**실제로 쓰이던 운영 기법**이다. 멈춤이 사용자에게 안 보인다.

**복잡하고 취약하다.** 그리고 예측 못 한 Full GC 는 막지 못한다.
[[reachability]] 의 덧에서 본 `System.gc()` 의 문제도 그대로다.

### 시도 4 — 표시 작업만 동시에 한다 (CMS)

[[generations]] 의 시도 3 을 **부분적으로** 실현한 것이다.

```
초기 표시   : STW (짧다)
동시 표시   : 애플리케이션과 같이 돈다 ← 여기가 긴 구간
재표시      : STW (짧다. 바뀐 것만)
동시 쓸기   : 같이 돈다
```

**멈춤이 극적으로 줄었다.** 긴 작업을 동시 구간으로 옮겼다.

그런데 **Compact 를 안 한다.** 그래서 [[reachability]] 의 단편화가 쌓이고,
결국 **단편화를 못 견디면 Full GC** 를 해버린다.
그 Full GC 는 **단일 스레드**라서 오히려 더 길다.

```
평소에는 멈춤이 짧다
그런데 어느 순간 수 초 멈춘다 (concurrent mode failure)
```

**최악의 경우가 더 나빠졌다.** 그리고 쓰기 배리어 비용과
동시 실행 때문에 **처리량이 10~20% 떨어진다.**

CMS 는 Java 9 에서 폐기 예정이 되고 Java 14 에서 제거됐다.

> 네 시도의 공통점: **힙을 통째로 다루는 전제를 유지했다.**
> 힙을 쪼개면 "일부만 수집"이 가능해지고, 그러면 멈춤을 **선택**할 수 있다.

## 3. 그래서 나온 것 — 힙을 쪼개고 예산을 정한다

### G1 — 리전으로 쪼개고 정지 시간을 목표로 둔다

Java 9 부터 기본값이다. 발상이 **두 가지**다.

**첫째, 힙을 같은 크기 리전으로 쪼갠다.**

```
기존: [ Eden | Survivor | Old ]        ← 크기와 위치가 고정
G1  : [E][ ][S][O][ ][O][E][H][O]...   ← 같은 크기, 역할은 동적
```

리전 하나가 1~32MB 다. 각 리전이 Eden 이나 Survivor 나 Old 역할을 맡고,
**그 역할이 바뀔 수 있다.**

**둘째, 정지 시간을 목표로 받는다.**

```bash file=terminal
java -XX:+UseG1GC -XX:MaxGCPauseMillis=200 MyApp
```

"200ms 안에 끝내라"고 **목표를 준다.** 그러면 G1 이
**그 안에 수집할 수 있는 만큼만** 리전을 고른다.

```
쓰레기가 가장 많은 리전부터 고른다
목표 시간 안에 끝낼 수 있는 개수만 담는다
→ 이름이 Garbage First 인 이유
```

네 고통과 대응시켜 보자.

| 고통 | 해결 |
| --- | --- |
| 코어가 남는데 한 스레드 | 병렬 + 동시 둘 다 쓴다 |
| 여전히 전면 통제 | 표시는 **동시에**, 회수는 **일부 리전만** |
| 멈춤을 예측할 수 없다 | **목표 시간을 주면** 그 안에 맞춘다 |
| 처리량은 좋은데 꼬리가 나쁘다 | 꼬리를 줄인다. **대신 처리량을 조금 낸다** |

**세 번째가 G1 의 핵심 기여**다. 예측 가능해졌다.
"보통 짧고 가끔 수 초"가 아니라 "거의 항상 200ms 안"이 된다.

### 처리량을 팔아 지연을 샀다

**공짜가 아니다.** 명확한 교환이 있다.

```
Parallel GC : 처리량 최고. 멈춤이 길고 예측 불가
G1          : 멈춤이 짧고 예측 가능. 처리량 5~15% 낮다
ZGC         : 멈춤이 1ms 이하. 처리량이 더 낮고 메모리를 더 쓴다
```

**배치 작업이면 Parallel 이 낫다.** 멈춤이 아무 문제가 안 되고
처리량이 전부이기 때문이다. Java 9 가 G1 을 기본값으로 삼은 것은
**서버 애플리케이션이 다수**라는 판단이다.

## 4. 어떻게 동작하나 — 다섯 GC 의 선택

```visual
id: gc-evolution-timeline
kind: step
title: 각 GC 가 무엇을 포기해 무엇을 얻었나
steps:
  - name: Serial GC — 아무것도 포기하지 않았다
    detail: 한 스레드가 전부 멈추고 치운다. 오버헤드가 없어 작은 힙에서는 가장 효율적이다. 지금도 컨테이너의 작은 JVM 기본값이 될 수 있다
    code: 단순함을 얻고 멈춤을 낸다
  - name: Parallel GC — 코어를 샀다
    detail: GC 를 여러 스레드로 나눈다. 멈춤이 코어 수에 거의 반비례해 줄어든다. 처리량 기준으로는 여전히 가장 좋다
    code: 멈춤 ÷ N · 처리량 최고
  - name: CMS — 처리량을 팔아 지연을 샀다 (제거됨)
    detail: 표시를 동시에 한다. 멈춤이 극적으로 줄었지만 Compact 를 안 해 단편화가 쌓이고 결국 더 긴 Full GC 가 터진다
    code: 평균은 좋고 최악은 나쁘다
  - name: G1 — 힙을 쪼개 예측을 샀다
    detail: 리전 단위로 수집하므로 한 번에 얼마나 할지 고를 수 있다. 목표 정지 시간을 받아 그 안에 맞춘다. Java 9 부터 기본값이다
    code: 예측 가능 · 처리량 5~15% 손실
  - name: ZGC — 읽기 배리어로 이동까지 동시에
    detail: 객체를 옮기는 작업까지 애플리케이션과 같이 한다. 멈춤이 힙 크기와 무관해져 1ms 이하가 된다. Java 15 부터 운영 가능
    code: 멈춤이 힙 크기와 무관
  - name: Generational ZGC — 가설을 다시 도입했다
    detail: ZGC 가 세대를 버렸는데 Java 21 에서 다시 넣었다. generations 의 약한 세대 가설이 여전히 유효하다는 것이 측정으로 확인됐다
    code: Java 21 · 처리량 회복
  - name: 그래서 전부 같은 축 위에 있다
    detail: 처리량과 지연 사이 어디에 설 것인가의 선택이다. 좋고 나쁜 것이 아니라 워크로드에 맞는 것이 있다
    code: 처리량 ↔ 지연
```

### G1 의 리전 모델이 푸는 것

```visual

  - name: 힙을 같은 크기 리전으로 쪼갠다
    detail: 1~32MB 짜리 조각으로 나누고 각 조각의 역할을 동적으로 정한다. 이 한 가지 변경에서 나머지가 전부 따라온다
    code: 역할이 고정이 아니다
    children:
      - name: 일부만 수집할 수 있다
        detail: 기존에는 Young 전체나 Old 전체가 단위였다. 리전이면 몇 개만 골라 수집할 수 있고 그 개수를 시간 예산에 맞춰 조절한다
        code: 수집 단위가 작아진다
        children:
          - name: 그래서 예측이 가능하다
            detail: 리전 하나를 수집하는 데 걸리는 시간을 과거 기록으로 추정한다. 목표가 200ms 면 그 안에 들어갈 개수만 고른다
            code: Pause Prediction Model
          - name: 쓰레기가 많은 것부터 고른다
            detail: 같은 시간을 쓰면 회수량이 많은 쪽이 이득이다. 이 전략이 이름의 유래다
            code: Garbage First
      - name: Young 과 Old 의 크기가 유동적이다
        detail: 역할이 리전마다 정해지므로 Young 이 커져야 하면 빈 리전을 Eden 으로 쓴다. -Xmn 을 손으로 맞출 필요가 줄어든다
        code: 경계가 고정이 아니다
        children:
          - name: 조기 승격이 완화된다
            detail: generations 에서 본 문제다. Survivor 가 작아 Old 로 직행하는 일이 리전 모델에서는 덜 생긴다
            code: Survivor 를 늘릴 수 있다
      - name: 복사가 곧 Compact 다
        detail: 리전의 생존자를 다른 빈 리전으로 복사하고 원래 리전을 통째로 비운다. 복사하면서 자동으로 압축되므로 단편화가 안 쌓인다
        code: Evacuation
        children:
          - name: CMS 의 약점을 풀었다
            detail: CMS 가 Compact 를 안 해 단편화로 터졌던 문제가 구조적으로 사라진다. 시도 4 의 한계가 여기서 해결된다
            code: 단편화 없음
      - name: 큰 객체를 위한 거대 리전
        detail: 리전 절반보다 큰 객체는 연속된 거대 리전에 넣고 Old 로 취급한다. generations 의 고통 4 에 대한 G1 의 답이다
        code: Humongous Region
        children:
          - name: 함정
            detail: 리전 크기의 절반을 조금 넘는 배열을 자주 만들면 거대 리전이 낭비되고 Full GC 를 유발할 수 있다. -XX:G1HeapRegionSize 를 키워 피한다
            code: 리전 크기를 넘는 배열
      - name: 대가 — 리전 간 참조를 추적해야 한다
        detail: 카드 테이블 하나로 안 되고 리전마다 기억 집합을 둔다. 메모리를 더 쓰고 쓰기 배리어가 더 무겁다
        code: Remembered Set
        children:
          - name: 처리량 손실의 정체
            detail: G1 이 Parallel 보다 5~15% 느린 이유가 대부분 이것이다. 공짜로 예측을 얻은 것이 아니다
            code: 배리어 비용
```

### ZGC 는 어떻게 1ms 를 달성했나

G1 도 **객체를 옮길 때는 멈춘다.** 옮기는 동안 참조가 바뀌면 안 되기 때문이다.
ZGC 는 그것까지 동시에 한다.

```
핵심: 읽기 배리어 (Load Barrier)

애플리케이션이 참조를 읽을 때마다 코드가 삽입된다
→ "이 객체가 이사 갔나?" 를 확인한다
→ 갔으면 새 주소로 고쳐서 돌려준다
→ 그래서 GC 가 옮기는 중에도 애플리케이션이 돌 수 있다
```

**멈춤이 힙 크기와 무관**해진다. 루트를 스캔하는 짧은 구간만 멈추고
나머지는 전부 동시에 한다.

```
힙 128GB 에서도 멈춤이 1ms 이하
```

**대가**는 읽기 배리어다. **참조를 읽을 때마다** 추가 코드가 돈다.
쓰기보다 읽기가 훨씬 많으므로 **처리량 손실이 G1 보다 크다.**
그리고 이사 정보를 담는 **추가 메모리**가 필요하다.

### 무엇을 고를까

```visual
id: gc-evolution-which-gc
kind: playground
title: 이 워크로드에는 어느 GC 인가
inputs:
  - { name: 워크로드, label: 어떤 애플리케이션, options: [웹 API 서버, 배치·데이터 처리, 힙 32GB 이상, 컨테이너 512MB, 캐시 서버, 게임·거래 서버] }
  - { name: 기준, label: 더 중요한 것, options: [p99 응답 시간, 처리량, 메모리 효율, 설정을 안 건드리는 것] }
outcomes:
  - when: { 워크로드: 웹 API 서버, 기준: p99 응답 시간 }
    result: G1 이 기본값이고 대개 맞다. MaxGCPauseMillis 로 목표를 주고 측정한다
    note: Java 9 부터 기본값인 이유가 이 경우다. 평균이 아니라 꼬리가 중요한 서버에 맞춰진 선택이다
  - when: { 워크로드: 배치·데이터 처리, 기준: 처리량 }
    result: Parallel GC 가 낫다. 멈춤이 아무 문제가 안 되고 처리량이 전부다
    note: G1 을 쓰면 5~15% 손해다. 배치에서 기본값을 그대로 쓰는 것이 오히려 손실인 드문 경우다
  - when: { 워크로드: 힙 32GB 이상, 기준: p99 응답 시간 }
    result: ZGC 를 검토한다. G1 도 이 크기에서는 멈춤이 수백 ms 로 늘어난다
    note: Java 21 의 Generational ZGC 는 처리량 손실도 많이 줄었다. 측정해서 G1 과 비교할 가치가 있다
  - when: { 워크로드: 컨테이너 512MB, 기준: 메모리 효율 }
    result: Serial GC 가 나을 수 있다. 작은 힙에서는 오버헤드가 없는 것이 이긴다
    note: JVM 이 CPU 와 메모리를 보고 자동으로 Serial 을 고르기도 한다. Docker 과목의 cgroups 에서 본 한도 인식이 이 판단에 쓰인다
  - when: { 워크로드: 캐시 서버, 기준: 처리량 }
    result: 생존율이 높아 세대 가설이 약하다. G1 과 ZGC 를 둘 다 측정해본다
    note: generations 의 덧에서 본 경우다. 거의 모든 객체가 오래 살면 Young 복사 비용이 커져 일반적 조언이 안 맞는다
  - when: { 워크로드: 게임·거래 서버, 기준: p99 응답 시간 }
    result: ZGC 나 Shenandoah 다. 수십 ms 도 허용되지 않는 영역이다
    note: 처리량을 분명히 내주는 선택이다. 그 대가를 치를 가치가 있는지가 비즈니스 요구에서 나온다
  - when: { 기준: 설정을 안 건드리는 것 }
    result: 기본값을 쓴다. 그리고 GC 로그를 켜두는 것만 한다
    note: 측정 없이 GC 를 바꾸는 것이 가장 흔한 잘못된 최적화다. 로그가 있으면 문제가 생겼을 때 판단할 근거가 생긴다
  - when: { 기준: 메모리 효율 }
    result: Serial 이나 Parallel 이다. G1 의 Remembered Set 과 ZGC 의 이사 정보가 추가 메모리를 쓴다
    note: 같은 힙 크기로 더 많은 객체를 담을 수 있다. 메모리가 빡빡한 환경에서 의미 있는 차이다
```

### 확인하는 법

```bash file=terminal
$ java -XX:+PrintCommandLineFlags -version
-XX:+UseG1GC -XX:InitialHeapSize=... -XX:MaxHeapSize=...

$ java -Xlog:gc,gc+heap=info MyApp
[0.4s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 24M->3M(256M) 2.8ms
[9.1s][info][gc] GC(8) Pause Young (Concurrent Start) 198M->41M(256M) 12.4ms
[9.1s][info][gc] GC(9) Concurrent Mark Cycle
[9.3s][info][gc] GC(9) Concurrent Mark Cycle 198.221ms
```

**`Pause` 가 붙은 것만 멈춤**이다.
`Concurrent` 는 애플리케이션과 같이 돌았으므로 멈춘 시간이 아니다.
이 구분을 모르면 **198ms 를 멈춤으로 오해**한다.

```bash file=terminal
$ java -Xlog:safepoint MyApp     # GC 외의 멈춤도 보인다
```

**GC 가 아닌 STW** 도 있다. 바이어스 락 해제, 스레드 덤프,
JIT 역최적화가 안전 지점에서 멈춘다.
"GC 를 줄였는데 아직 튄다"면 이것을 본다.

## 5. 이것도 끝이 아니다 — PART 3 이 여기서 끝난다

세 글을 묶으면 이렇게 된다.

```
reachability   "누가 쓰나"를 "루트에서 닿나"로 뒤집어 순환을 풀었다
generations    수명 분포의 규칙을 이용해 전체 탐색을 피했다
gc-evolution   힙을 쪼개 멈춤을 선택 가능하게 만들었다
```

전부 **"비용을 어디로 옮길까"**였다.
참조 카운팅은 평소에 조금씩, Mark-Sweep 은 GC 때 몰아서,
동시 GC 는 배리어로 평소에 조금씩 **다시** 옮겼다.

**공짜는 없고 어디에 낼지만 고를 수 있다.**

그런데 지금까지의 결론이 하나 있다.
**객체를 덜 만드는 것은 여전히 유효한 최적화**다.
Young GC 가 싸졌어도 공짜는 아니고, Old 로 승격되면 비싸진다.

그러면 **어디서 객체가 많이 만들어지나.**

```java file=WhereObjectsPile.java
String result = "";
for (String s : items) {
    result += s;        // 반복마다 새 String 이 만들어진다
}
```

**매일 쓰는 코드**에서 만들어진다.
문자열을 합치고, 리스트에 담고, `int` 를 `Integer` 로 박싱하고.

그리고 `HashMap` 에 넣을 때 무슨 일이 일어나는지,
`ArrayList` 가 커질 때 무슨 비용이 드는지,
`String` 리터럴이 왜 `==` 로 비교되기도 하는지 —
전부 **이 PART 에서 배운 메모리 모델 위**에서 설명된다.

PART 4 에서 **문자열과 컬렉션**으로 간다.

## 덧 — 흔한 오해

### "최신 GC 가 항상 낫다"

**워크로드에 달렸다.** 처리량 기준으로는 Parallel 이 여전히 최고다.

```
배치 작업에 ZGC 를 쓰면
→ 멈춤은 1ms (아무 가치 없다. 사용자가 없으니)
→ 처리량 손실 (전체 작업 시간이 늘어난다)
→ 순손실
```

**기본값을 그대로 쓰는 것이 손실인 드문 경우**가 배치다.
Java 9 가 G1 을 기본값으로 삼은 것은 서버가 다수라는 판단이고,
내 워크로드가 서버가 아니면 그 판단이 안 맞는다.

### "G1 을 쓰면 Full GC 가 안 난다"

**난다.** 그리고 났을 때 더 아프다.

```
Pause Full (G1 Compaction Pause)
```

G1 이 동시 수집을 **따라가지 못하면** Full GC 로 떨어진다.
할당 속도가 수집 속도보다 빠를 때(allocation failure) 그렇다.

그리고 **거대 리전 문제**가 흔한 원인이다.
리전 절반보다 큰 배열을 자주 만들면 거대 리전이 쌓이고
동시 수집이 그것을 제대로 못 치운다.

```bash file=terminal
$ java -XX:G1HeapRegionSize=32m MyApp    # 리전을 키워 거대 객체를 줄인다
```

**Full GC 가 보이면 그것 자체가 신호**다.
G1 에서 Full GC 는 정상 동작이 아니라 **밀렸다는 뜻**이다.

### "GC 튜닝으로 성능 문제를 해결한다"

**대부분은 코드 문제**다. GC 옵션은 마지막에 본다.

```
순서
1. 누수인지 확인한다 (Full GC 후에도 Old 가 안 줄어드나)
2. 객체를 과하게 만드는 곳을 찾는다 (할당 프로파일링)
3. 힙 크기를 맞춘다
4. 그래도 안 되면 GC 종류와 옵션을 본다
```

**1번과 2번이 효과의 대부분**이다.
GC 옵션을 수십 개 뒤지는 것보다 **상한 없는 캐시 하나를 고치는 것**이
훨씬 크게 바꾼다.

그리고 **측정 없이 옵션을 바꾸지 않는다.**
`-XX:` 로 시작하는 옵션을 블로그에서 복사해 붙이는 것이
가장 흔한 잘못된 최적화다. 기본값은 많은 측정의 결과물이고,
내 측정 없이 이기기 어렵다.
