서버 한 대를 여러 용도로 나눠 쓰려는 시도는 계속 **더 가벼운 쪽**으로 움직였다.
물리 분리 → 가상 머신 → 컨테이너로 내려오는 동안 무엇이 빨라졌고
**무엇을 포기했는지**를 따진다.

"컨테이너가 VM 보다 좋다"가 아니다. **다른 것을 포기한 다른 선택**이다.
그 교환을 알아야 어디에 무엇을 쓸지 판단할 수 있다.

## 0. 들어가기 전에 — 핵심 용어

- **하이퍼바이저(hypervisor)**: 물리 하드웨어를 가상 하드웨어로 쪼개 여러 OS 를 돌리는 층.
- **게스트 OS**: VM 안에서 도는 운영체제. 자기 커널을 가진다.
- **호스트 OS**: 실제 하드웨어 위에서 도는 운영체제.
- **오버헤드(overhead)**: 본래 일과 상관없이 구조 때문에 더 드는 비용. 메모리, 기동 시간, CPU.
- **집적도(density)**: 서버 한 대에 몇 개를 올릴 수 있는가.

한 줄 그림: **VM 은 하드웨어를 흉내 내고, 컨테이너는 OS 를 흉내 낸다. 흉내 내는 층이 낮을수록 무겁다.**

비유하자면 **건물 나누기**다. 물리 서버는 **단독주택**이다. 완전히 독립이지만
집마다 땅과 보일러와 수도관이 따로 든다. VM 은 **아파트**다. 땅은 하나지만
세대마다 보일러와 배관이 따로 있다. 컨테이너는 **셰어하우스의 방**이다.
방문은 잠기지만 보일러와 배관은 공유한다. 방 하나 더 만드는 비용이 거의 없다.
대신 **보일러가 고장 나면 전부 춥다.**

## 1. 그전엔 어떻게 했나 — 물리 서버의 고통

2000년대 초 서버실은 "앱 하나에 서버 한 대"가 기본이었다.

### 고통 1 — 자원이 놀고 있다

웹 서버 한 대의 평균 CPU 사용률이 **10% 를 밑도는 경우가 흔했다.**
피크를 견디려고 사양을 맞추니 평소에는 90% 가 논다.

그렇다고 한 대에 여러 앱을 올리면 다른 문제가 생긴다.

### 고통 2 — 섞어 놓으면 서로를 망가뜨린다

[[isolation-history]] 에서 본 네 고통이 그대로 나온다.

```
포트 충돌        : 둘 다 80 번을 원한다
라이브러리 충돌   : 한쪽은 libfoo 1.x, 한쪽은 2.x
자원 독점        : 하나가 메모리를 다 먹으면 다른 것도 죽는다
장애 전파        : OS 를 재부팅하면 전부 내려간다
```

그래서 "안전하게 가려면 서버를 나눠라"가 상식이 됐고, 고통 1 로 돌아간다.

### 고통 3 — 서버를 늘리는 데 몇 주가 걸린다

장비를 사고, 랙에 꽂고, OS 를 깔고, 네트워크를 잡는다.
**트래픽이 늘어나는 속도를 사람 손이 못 따라간다.**

세 고통의 뿌리는 하나다. **격리의 단위가 하드웨어**다.
나누려면 쇠붙이를 하나 더 사야 한다.

## 2. 이렇게 피해봤다 — 가상화의 등장

### 시도 1 — 전가상화 (VMware, 2001)

하이퍼바이저가 **가상의 하드웨어**를 만들어준다. 게스트 OS 는 자기가
진짜 기계 위에 있다고 믿는다. OS 를 수정하지 않아도 된다.

고통 1·2·3 이 한 번에 풀린다. 한 대에 여러 OS 를 올리고,
각자 포트와 라이브러리를 따로 쓰고, 새 서버는 몇 분이면 만든다.

대가는 **성능**이었다. 게스트의 명령을 하이퍼바이저가 중간에서 번역해야 했다.
특히 디스크와 네트워크가 느렸다.

### 시도 2 — 반가상화와 하드웨어 지원 (Xen 2003, Intel VT-x 2005)

게스트 OS 를 조금 고쳐 "나는 가상화돼 있다"는 걸 알게 하면(반가상화)
번역이 줄어 빨라진다. 이후 CPU 가 가상화를 직접 지원하면서
**성능 문제는 대체로 해결됐다.**

지금 클라우드의 인스턴스가 전부 이 방식이다.

그런데 남는 비용이 있다. **게스트 OS 그 자체**다.

| 항목 | VM 한 대당 |
| --- | --- |
| 메모리 | 커널 + 시스템 데몬으로 수백 MB |
| 디스크 | OS 이미지로 수 GB |
| 기동 | 부팅 과정 전체. 수십 초 |
| 관리 | OS 마다 패치·보안 업데이트가 따로 |

앱 하나가 50MB 인데 **그걸 담은 VM 은 2GB** 다.
서버 한 대에 VM 을 20개 올리면 그중 상당량이 OS 복사본이다.

### 시도 3 — 같은 OS 안에서 나누기 (Jail, LXC)

"어차피 전부 리눅스인데 커널을 왜 여러 벌 띄우나"에서 출발한 발상이다.
[[isolation-history]] 에서 본 namespace 와 cgroup 이 그 답이다.

이 방향은 기술적으로 맞았지만 2013년까지 널리 안 쓰였다.
배포와 공유 문제가 남아 있었기 때문이다.

> 세 시도의 흐름: **가상화하는 층을 점점 위로 올렸다.**
> 하드웨어를 흉내 내다가, OS 를 흉내 내는 쪽으로.

## 3. 그래서 나온 것 — 커널을 공유한다

컨테이너는 게스트 OS 를 **통째로 빼버린다.**

```
VM                                컨테이너
┌─────────┐ ┌─────────┐          ┌─────┐ ┌─────┐ ┌─────┐
│   앱    │ │   앱    │          │ 앱  │ │ 앱  │ │ 앱  │
│ 라이브러리│ │ 라이브러리│          │ 라이브러리 (이미지 안) │
│ 게스트OS │ │ 게스트OS │  ← 이게   └─────┘ └─────┘ └─────┘
└─────────┘ └─────────┘    사라짐  ──────────────────────
──────────────────────            │   호스트 커널 (하나)  │
│    하이퍼바이저      │            ──────────────────────
──────────────────────            │      하드웨어        │
│      하드웨어        │            ──────────────────────
──────────────────────
```

고통과 대응시켜 보자.

| 고통 | VM 의 해결 | 컨테이너의 해결 |
| --- | --- | --- |
| 자원이 논다 | 한 대에 여러 OS | 한 OS 에 수십~수백 개. **집적도가 한 자릿수 배 더 높다** |
| 섞으면 망가진다 | 게스트 OS 로 완전 분리 | namespace 로 분리. **대부분의 경우 충분하다** |
| 늘리는 데 오래 걸린다 | 몇 분 | **수백 ms** |

```visual
id: vm-vs-container-stack
kind: step
title: 가상화하는 층이 올라갈수록 가벼워진다
steps:
  - name: 물리 서버
    detail: 격리 단위가 하드웨어다. 나누려면 쇠붙이를 하나 더 사야 한다. 평균 CPU 사용률이 10% 를 밑돌기도 했다
  - name: 전가상화 (2001)
    detail: 하이퍼바이저가 가상 하드웨어를 만든다. 게스트 OS 를 안 고쳐도 되지만 명령을 번역해야 해서 느렸다
  - name: 하드웨어 지원 가상화 (2005)
    detail: CPU 가 가상화를 직접 돕는다. 속도 문제는 대체로 해결. 다만 게스트 OS 한 벌의 비용은 남는다
    code: "VM 당 메모리 수백 MB · 디스크 수 GB · 부팅 수십 초"
  - name: 컨테이너
    detail: 게스트 OS 를 빼고 호스트 커널을 공유한다. 흉내 내는 층이 하드웨어에서 OS 로 올라갔다
    code: "컨테이너당 오버헤드 거의 없음 · 기동 수백 ms"
  - name: 경량 VM (2018~)
    detail: 격리를 되찾으려고 다시 VM 으로. 다만 기능을 최소화해 100ms 대로 뜬다. 서버리스가 이 방식이다
```

숫자로 보면 차이가 분명하다.

| | VM | 컨테이너 |
| --- | --- | --- |
| 기동 시간 | 수십 초 (부팅) | 수백 ms (프로세스 시작) |
| 디스크 | 수 GB | 수십 MB (베이스는 공유) |
| 메모리 오버헤드 | 수백 MB | 거의 없음 |
| 한 호스트에 | 수십 개 | 수백 개 |

**기동 시간이 특히 성격을 바꿨다.** 수십 초면 "미리 띄워두고 쓰는 것"이지만,
수백 ms 면 **필요할 때 띄우고 끝나면 버리는 것**이 된다.
CI 가 테스트마다 깨끗한 DB 를 띄우고, 오토스케일링이 초 단위로 반응하는 것이
여기서 가능해졌다.

## 4. 어떻게 동작하나 — 무엇을 공유하고 무엇을 나누는가

경계가 어디인지 정확히 보는 게 중요하다.

```visual
id: vm-vs-container-boundary
kind: structure
title: 컨테이너에서 나뉘는 것과 공유되는 것
nodes:
  - name: 나뉜다 (namespace 가 담당)
    detail: 컨테이너마다 따로 가진다. 안에서 보면 자기 것만 보인다
    children:
      - name: 프로세스 목록
        detail: 안에서 ps 를 치면 자기 프로세스만. 컨테이너의 메인 프로세스가 PID 1 이다
      - name: 파일 시스템
        detail: 이미지 층을 겹쳐 만든 자기만의 루트
      - name: 네트워크
        detail: 자기 인터페이스와 포트 공간. 그래서 둘 다 80 번을 쓸 수 있다
      - name: 호스트명 · IPC · UID 매핑
        detail: 각각 uts, ipc, user namespace
  - name: 공유한다 (여기가 VM 과 갈리는 지점)
    detail: 호스트와 같은 것을 쓴다. 가볍지만 격리가 얇아지는 이유
    children:
      - name: 커널
        detail: 컨테이너 안 프로세스가 호스트 커널에 직접 시스템 콜을 날린다. 중간 번역이 없어 빠르다
        code: uname -r   # 이미지가 우분투여도 호스트 커널 버전이 나온다
      - name: CPU 스케줄러
        detail: 호스트 스케줄러가 전부를 함께 스케줄링한다. cgroup 으로 비율만 제한한다
      - name: 커널 파라미터 일부
        detail: sysctl 값 상당수가 호스트 것이다. 컨테이너에서 못 바꾸는 것이 많다
      - name: 시스템 시간
        detail: 기본적으로 호스트 시계를 그대로 본다
```

**커널을 공유한다**는 한 가지 사실에서 장점과 단점이 **동시에** 나온다.

| 같은 사실에서 나오는 것 | |
| --- | --- |
| 장점 | 게스트 OS 가 없다 → 가볍고 빠르다 |
| 장점 | 시스템 콜이 직접 간다 → 번역 오버헤드가 없다 |
| 단점 | 커널 취약점이 격리를 뚫는다 |
| 단점 | 호스트와 다른 커널을 못 쓴다 (윈도우에서 리눅스 컨테이너 불가) |
| 단점 | 커널 파라미터를 컨테이너별로 못 바꾼다 |

이 표 하나가 이 글의 결론이다. **가벼움과 격리 강도는 같은 손잡이의 양쪽 끝**이다.

## 5. 이것도 끝이 아니다 — 포기한 것을 되찾으려는 시도

격리를 포기한 대가가 문제가 되는 곳이 있다.

**클라우드 사업자**는 서로 모르는 고객의 코드를 한 호스트에 올린다.
커널 취약점 하나로 옆 고객의 데이터가 샌다면 사업이 끝난다.

그래서 **다시 VM 으로 돌아가되, 가볍게** 만드는 시도가 나왔다.

| | Firecracker | Kata Containers | gVisor |
| --- | --- | --- | --- |
| 방식 | 최소 기능 VM | 컨테이너를 VM 으로 감쌈 | 사용자 공간 커널로 시스템 콜 가로채기 |
| 기동 | 100ms 대 | 수백 ms | 빠름 |
| 격리 | VM 수준 | VM 수준 | 중간 |

AWS Lambda 와 Fargate 가 Firecracker 위에서 돈다.
**"컨테이너처럼 쓰지만 VM 으로 격리"** 가 지금의 답이다.

```visual
id: vm-vs-container-choose
kind: playground
title: 상황에 따라 무엇을 고르는가
inputs:
  - name: situation
    label: 상황
    options: [내 서비스 여러 개, 남이 올린 코드 실행, 다른 커널이 필요, 초당 수백 번 띄움]
  - name: option
    label: 선택지
    options: [컨테이너, 일반 VM, 경량 VM]
outcomes:
  - { when: { situation: 내 서비스 여러 개, option: 컨테이너 }, result: "맞다. 같은 신뢰 수준이라 namespace 격리로 충분하다" }
  - { when: { situation: 내 서비스 여러 개, option: 일반 VM }, result: "과하다. 게스트 OS 비용만큼 집적도를 잃는다" }
  - { when: { situation: 내 서비스 여러 개, option: 경량 VM }, result: "과하다. 얻는 격리에 비해 복잡도가 크다" }
  - { when: { situation: 남이 올린 코드 실행, option: 컨테이너 }, result: "위험하다. 커널 취약점 하나로 호스트가 뚫린다", note: "신뢰 경계로는 부족" }
  - { when: { situation: 남이 올린 코드 실행, option: 일반 VM }, result: "안전하다. 다만 기동이 수십 초라 쓰임새가 제한된다" }
  - { when: { situation: 남이 올린 코드 실행, option: 경량 VM }, result: "맞다. VM 수준 격리에 100ms 대 기동. 서버리스가 이 조합이다" }
  - { when: { situation: 다른 커널이 필요, option: 컨테이너 }, result: "불가능하다. 커널은 호스트 것 하나뿐이다" }
  - { when: { situation: 다른 커널이 필요, option: 일반 VM }, result: "맞다. 게스트가 자기 커널을 가진다" }
  - { when: { situation: 다른 커널이 필요, option: 경량 VM }, result: "가능하다. 다만 커널을 고를 자유는 제한적이다" }
  - { when: { situation: 초당 수백 번 띄움, option: 컨테이너 }, result: "맞다. 수백 ms 라 쓰고 버리는 용도가 성립한다" }
  - { when: { situation: 초당 수백 번 띄움, option: 일반 VM }, result: "불가능하다. 부팅에 수십 초가 든다" }
  - { when: { situation: 초당 수백 번 띄움, option: 경량 VM }, result: "가능하다. 컨테이너보다는 느리다" }
```

반대 방향의 천장도 있다. 컨테이너는 **리눅스 커널 기능**이라,
Windows 와 macOS 에서는 리눅스 VM 을 하나 띄워야 한다.
"컨테이너는 VM 보다 가볍다"가 그 환경에서는 절반만 참이다.

다음 글에서는 **컨테이너가 프로세스 하나**라는 사실이
실제 설계에 어떤 제약을 거는지 본다. [[container-is-a-process]] 로 이어진다.

## 자기 점검

- VM 이 무거운 이유를 "흉내 내는 층"의 높이로 설명하면?
- 컨테이너가 빠른 이유와 격리가 약한 이유가 **같은 사실**에서 나온다. 그 사실과 그로부터 나오는 결과 네 가지를 들면?
- 기동 시간이 수십 초에서 수백 ms 로 줄면 **쓰임새 자체**가 어떻게 달라지는가?
- 클라우드 서버리스가 컨테이너 대신 경량 VM 을 쓰는 이유는?
- 윈도우에서 리눅스 컨테이너를 돌릴 때 "컨테이너가 VM 보다 가볍다"는 주장이 왜 흔들리는가?

## 덧 — 흔한 오해

### "컨테이너가 VM 을 대체한다"

층이 다르다. 실제로는 **VM 위에 컨테이너를 올린다.**

```
클라우드 인스턴스(VM) ──► 그 안에 컨테이너 수십 개
```

쿠버네티스 노드가 대부분 EC2 인스턴스다. VM 이 **하드웨어와 테넌트를 가르고**,
컨테이너가 **그 안에서 앱을 가른다.** 역할이 겹치지 않는다.

### "컨테이너는 보안 경계다"

같은 신뢰 수준 안에서는 충분하다. **신뢰 경계로는 부족하다.**

```
내 서비스 A 와 내 서비스 B 를 나눈다        → 컨테이너로 충분
남이 올린 코드를 내 서버에서 돌린다          → 컨테이너만으로는 위험
고객 A 와 고객 B 의 코드를 한 호스트에 올린다 → 경량 VM 을 쓴다
```

판단 기준 하나면 된다. **"안에서 도는 코드를 내가 신뢰하는가."**

### "VM 이 느리니까 요즘은 안 쓴다"

하드웨어 가상화 지원이 들어간 뒤로 **VM 의 CPU 성능은 네이티브와 거의 같다.**
VM 의 진짜 비용은 속도가 아니라 **게스트 OS 한 벌의 메모리·디스크·관리 부담**이다.

그래서 "VM 20개 vs 컨테이너 20개"는 성능 차이가 아니라 **집적도 차이**로 갈린다.
같은 하드웨어에 컨테이너는 몇 배를 더 올린다. 거기서 비용이 난다.
