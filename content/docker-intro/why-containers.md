배포 사고의 상당수는 코드 문제가 아니다. **코드는 그대로인데 환경이 달라서** 생긴다.

이 글은 그 고통이 구체적으로 어떤 모양이었고, 사람들이 어떻게 피해보려 했고,
왜 결국 "환경을 통째로 묶는" 방법으로 갔는지를 따라간다.

## 0. 들어가기 전에 — 핵심 용어

- **런타임(runtime)**: 코드를 실제로 실행해주는 것. JVM, Node.js, Python 인터프리터.
- **의존성(dependency)**: 내 코드가 돌려면 있어야 하는 남의 것. 라이브러리, 시스템 패키지.
- **환경(environment)**: 런타임 + 의존성 + OS 설정 + 환경변수를 다 합친 것. 코드가 발 딛고 선 땅.
- **이미지(image)**: 그 환경 전부를 파일 묶음으로 고정해둔 것. 읽기 전용이다.
- **컨테이너(container)**: 이미지를 띄운 프로세스. 실제로 도는 것.

한 줄 그림: **코드만 옮기지 말고, 코드가 딛고 선 땅까지 통째로 옮긴다.**

비유하자면 **이사**다. 가구만 트럭에 싣고 가면 새 집에서 콘센트 위치가 달라
TV 를 못 켠다. 수도 규격이 달라 세탁기가 안 맞는다. 이사 전에 아무리 꼼꼼히
적어가도 "그 집에만 있던 것"은 목록에 안 적힌다. 컨테이너는 **집을 통째로 들어
옮기는** 쪽을 택한 것이다. 땅만 빌리면 집 안은 어디서나 똑같다.

## 1. 그전엔 어떻게 했나 — 환경 차이의 고통

배포 절차서는 보통 이렇게 생겼다.

```bash file=deploy.md
# 1. Java 17 설치
sudo apt install openjdk-17-jdk

# 2. 애플리케이션 복사
scp app.jar server:/opt/app/

# 3. 실행
java -jar /opt/app/app.jar
```

세 줄이면 끝날 것 같다. 실제로는 그렇지 않다.

### 고통 1 — 버전이 "대충" 같다

`openjdk-17-jdk` 는 배포판마다 다른 빌드를 준다.
개발 PC 는 17.0.9, 서버는 17.0.2 일 수 있다. 보통은 괜찮다.
그러다 **17.0.5 에서 고쳐진 버그**를 밟으면 "서버에서만" 터진다.

```bash file=terminal
# 개발 PC
$ java -version
openjdk version "17.0.9" 2023-10-17

# 서버
$ java -version
openjdk version "17.0.2" 2022-01-18
```

절차서에는 "Java 17" 이라고만 적혀 있다. **틀린 말이 아니다.**
그런데 이 둘은 다른 것이다. 어디까지 적어야 "같다"고 할 수 있는지가 애초에 불분명하다.

### 고통 2 — 적히지 않은 의존성

애플리케이션이 이미지 처리를 한다고 하자. 개발 PC 에서는 잘 된다.
서버에 올리면 `UnsatisfiedLinkError` 가 난다.

```
java.lang.UnsatisfiedLinkError: /tmp/opencv.so:
  libgomp.so.1: cannot open shared object file
```

`libgomp` 는 개발 PC 에 **다른 프로그램이 설치되면서 딸려 들어온 것**이다.
아무도 그걸 설치한 기억이 없고, 그래서 절차서에도 없다.

이게 환경 차이의 진짜 성격이다. **빠뜨린 것이 아니라, 있는 줄도 몰랐던 것**이다.
"꼼꼼히 적으면 된다"로는 안 풀린다.

### 고통 3 — 서버끼리도 다르다

서버가 한 대면 그나마 낫다. 열 대가 되면 **열 대가 서로 다르다.**

```
web-01   2021년 구축. 그 뒤로 패치만
web-02   2023년 증설. 베이스 OS 가 다르다
web-03   장애 때 급하게 복구. 누군가 손으로 뭘 고쳤다
```

"web-03 에서만 느리다" 같은 문제가 생기면 **원인을 찾는 데만 며칠**이 간다.
서버가 조금씩 달라지는 이 현상을 설정 드리프트(configuration drift)라 부른다.

세 고통은 사실 **하나**다. **환경이 코드 밖에 있고, 아무도 그 전체를 모른다.**
사람의 기억과 문서에만 있으니 재현할 수가 없다.

```visual
id: why-containers-drift
kind: structure
title: 환경이 코드 밖에 있으면 따라오는 것들
nodes:
  - name: 환경이 코드 밖에 있다
    detail: 런타임·라이브러리·OS 설정이 서버마다 따로 쌓인다. 전체를 아는 사람이 없다
    children:
      - name: 고통 1 · 버전이 대충 같다
        detail: 적힌 대로 Java 17 은 맞지만 패치 버전이 다르다. 어디까지 맞춰야 하는지 기준이 없다
        code: "개발 17.0.9  /  서버 17.0.2"
      - name: 고통 2 · 적히지 않은 의존성
        detail: 딸려 들어온 시스템 라이브러리는 설치한 기억이 없어 문서에도 없다
        code: libgomp.so.1 cannot open shared object file
      - name: 고통 3 · 서버끼리 다르다
        detail: 구축 시기와 장애 복구 이력이 달라 같은 코드가 서버마다 다르게 돈다
```

## 2. 이렇게 피해봤다 — 절차를 재현하려던 시도들

사람들이 이 고통을 몰랐던 게 아니다. 20년 가까이 나름의 방법을 찾았다.

### 시도 1 — 절차서를 더 자세히 쓴다

가장 먼저 하는 일이고, 가장 먼저 실패한다.

문제는 성실성이 아니다. **모르는 것은 적을 수 없다.** 고통 2가 보여준 그대로다.
그리고 문서는 서버가 바뀌어도 자동으로 안 바뀐다. 쓰는 순간부터 낡기 시작한다.

### 시도 2 — 셸 스크립트로 자동화한다

절차서를 스크립트로 바꾸면 적어도 사람이 빠뜨리지는 않는다.

```bash file=setup.sh
#!/bin/bash
apt-get install -y openjdk-17-jdk libgomp1
mkdir -p /opt/app
cp app.jar /opt/app/
```

**한 번 돌릴 때는 잘 된다.** 두 번 돌리면 문제가 생긴다.
이미 설치된 상태에서 또 돌리면 어떻게 되는지 매번 따져야 한다.
`mkdir` 은 실패하고, 설정 파일에 같은 줄이 두 번 들어간다.

그리고 **출발 상태를 가정한다.** 깨끗한 우분투를 전제로 쓴 스크립트는
이미 뭔가 깔린 서버에서 다르게 동작한다.

### 시도 3 — 설정 관리 도구 (Ansible, Chef, Puppet)

여러 번 돌려도 같은 결과가 되게(멱등성) 만든 도구들이다. 시도 2의 문제를 제대로 푼다.

```yaml file=playbook.yml
- name: Java 설치
  apt:
    name: openjdk-17-jdk=17.0.9+9-1
    state: present
```

버전까지 고정할 수 있다. 수백 대를 한 번에 맞출 수 있다.
**실제로 훌륭한 도구이고 지금도 쓰인다.**

그런데 한계가 남는다. 이 도구들은 **"같은 절차를 재현"** 한다.

```
깨끗한 서버  + 절차 →  상태 A
뭔가 깔린 서버 + 절차 →  상태 A'   ← 미묘하게 다르다
```

출발 상태가 다르면 도착 상태도 다르다. 그리고 패키지 저장소가 바뀌거나
외부 URL 이 404 가 되면 **어제 되던 절차가 오늘 안 된다.**

세 시도가 어디까지 풀었는지 직접 바꿔보면 경계가 보인다.

```visual
id: why-containers-attempts
kind: playground
title: 어떤 방법이 어떤 고통을 푸는가
inputs:
  - name: way
    label: 방법
    options: [절차서, 셸 스크립트, 설정 관리 도구, 이미지]
  - name: pain
    label: 고통
    options: [버전이 대충 같다, 적히지 않은 의존성, 서버끼리 다르다]
outcomes:
  - { when: { way: 절차서, pain: 버전이 대충 같다 }, result: "적을 수는 있다. 다만 아무도 끝까지 안 적는다" }
  - { when: { way: 절차서, pain: 적히지 않은 의존성 }, result: "못 푼다. 있는 줄 모르는 것은 적을 수 없다" }
  - { when: { way: 절차서, pain: 서버끼리 다르다 }, result: "못 푼다. 문서는 서버가 바뀌어도 안 바뀐다" }
  - { when: { way: 셸 스크립트, pain: 버전이 대충 같다 }, result: "푼다. 버전을 박아 설치할 수 있다" }
  - { when: { way: 셸 스크립트, pain: 적히지 않은 의존성 }, result: "못 푼다. 적어야 설치된다는 점은 절차서와 같다" }
  - { when: { way: 셸 스크립트, pain: 서버끼리 다르다 }, result: "반쯤. 두 번 돌리면 결과가 달라진다", note: "멱등하지 않다" }
  - { when: { way: 설정 관리 도구, pain: 버전이 대충 같다 }, result: "푼다. 버전 고정이 기본 기능이다" }
  - { when: { way: 설정 관리 도구, pain: 적히지 않은 의존성 }, result: "못 푼다. 여전히 내가 아는 것만 적는다" }
  - { when: { way: 설정 관리 도구, pain: 서버끼리 다르다 }, result: "거의 푼다. 다만 출발 상태가 다르면 도착도 미묘하게 다르다" }
  - { when: { way: 이미지, pain: 버전이 대충 같다 }, result: "푼다. 그 버전이 이미 들어 있다. 설치가 일어나지 않는다" }
  - { when: { way: 이미지, pain: 적히지 않은 의존성 }, result: "푼다. 빌드 때 거기 있던 파일이 그냥 같이 담긴다. 알 필요가 없다", note: "이게 결정적 차이" }
  - { when: { way: 이미지, pain: 서버끼리 다르다 }, result: "푼다. 서버는 풀어서 돌리기만 한다. 서버 상태가 무관해진다" }
```

> 세 시도의 공통점: **절차를 정확하게 만들려 했다.**
> 컨테이너는 방향을 틀었다. 절차가 아니라 **결과물**을 고정한다.

## 3. 그래서 나온 것 — 결과를 고정한다

이미지는 "이렇게 설치해라"가 아니라 **"설치가 끝난 상태"** 그 자체다.

```dockerfile file=Dockerfile
FROM eclipse-temurin:17.0.9_9-jre-alpine
RUN apk add --no-cache libgomp
COPY app.jar /opt/app/app.jar
ENTRYPOINT ["java", "-jar", "/opt/app/app.jar"]
```

이걸 빌드하면 **파일 묶음 하나**가 나온다. 그 묶음을 어디서 풀든 같은 파일이 나온다.
절차를 다시 밟지 않으니 출발 상태라는 개념 자체가 없다.

세 고통이 어떻게 사라졌는지 대응시켜 보자.

| 고통 | 절차 기반 도구의 대응 | 이미지의 해결 |
| --- | --- | --- |
| 버전이 대충 같다 | 버전을 명시해 설치 | 그 버전이 **이미 들어 있다**. 설치가 안 일어난다 |
| 적히지 않은 의존성 | 알아내서 추가 (모르면 못 함) | 빌드 때 들어간 것이 **전부 같이 옮겨진다** |
| 서버끼리 다르다 | 전체에 같은 절차 적용 | 서버는 이미지를 풀어 돌리기만 한다. 서버 상태가 무관해진다 |

고통 2 가 특히 중요하다. 절차 기반으로는 **내가 모르는 의존성을 적을 수 없다.**
이미지는 빌드 시점에 그 파일이 거기 있었으면 **그냥 같이 담긴다.** 알 필요가 없다.

## 4. 어떻게 동작하나 — 빌드는 한 번, 실행은 여러 번

핵심은 **빌드와 실행이 분리된다**는 것이다.

```visual
id: why-containers-build-once
kind: step
title: 환경을 만드는 일은 한 번만 일어난다
steps:
  - name: Dockerfile 작성
    detail: 어떤 베이스에 무엇을 더할지 적는다. 이건 여전히 절차다
    code: FROM eclipse-temurin:17.0.9_9-jre-alpine
  - name: 빌드
    detail: 절차를 한 번 실행해 결과물을 만든다. 여기서 "설치"가 일어난다
    code: docker build -t myapp:1.0 .
  - name: 이미지
    detail: 설치가 끝난 파일 묶음. 읽기 전용이고 더 이상 변하지 않는다
  - name: 레지스트리로 전송
    detail: 그 묶음을 올려둔다. 받는 쪽은 절차를 모른다
    code: docker push myapp:1.0
  - name: 실행
    detail: 어느 서버든 받아서 띄운다. 설치 과정이 없으므로 서버 상태가 영향을 주지 않는다
    code: docker run myapp:1.0
```

그래서 이런 사실이 따라 나온다. **운영 서버에는 Java 가 깔려 있지 않아도 된다.**
Java 는 이미지 안에 있다. 서버에 필요한 것은 컨테이너를 돌릴 수 있는 능력뿐이다.

서버를 "앱을 설치하는 곳"에서 **"이미지를 돌리는 곳"** 으로 바꾼 것이
이 변화의 실체다. 서버가 단순해지니 서버를 늘리는 것도 쉬워진다.

## 5. 이것도 끝이 아니다 — 새 고통

환경 차이는 잡혔다. 그런데 새로운 문제가 따라온다.

**이미지가 커진다.** JDK 를 통째로 담으면 수백 MB 다. 코드 한 줄 고칠 때마다
그걸 다시 전송하면 배포가 느려진다. 이 고통이 **레이어**를 부른다.

**격리가 완벽하지 않다.** 컨테이너는 호스트 커널을 공유한다. VM 처럼 벽이 두껍지 않다.
어디까지 나뉘고 어디부터 공유되는지 알아야 한다. 그 답이 [[isolation-history]] 와
[[vm-vs-container]] 에 있다.

**상태를 어디에 둘지 모른다.** 이미지는 읽기 전용인데 DB 는 데이터를 써야 한다.
컨테이너를 지우면 그 데이터는 어떻게 되는가.

다음 글에서 격리가 어떻게 만들어졌는지부터 본다.
"컨테이너는 Docker 가 발명했다"는 흔한 오해를 거기서 깬다.

## 자기 점검

- 설치 스크립트를 아무리 꼼꼼히 써도 환경 차이가 남는 이유를, 고통 2 를 들어 설명하면?
- Ansible 같은 설정 관리 도구도 "절차를 재현"한다. 이미지와 무엇이 다른가?
- 운영 서버에 Java 를 설치하지 않아도 자바 앱이 도는 것이 어떻게 가능한가?
- 이미지가 환경 차이를 없앴다면, 그래도 "운영에서만 터지는 버그"가 남는다면 원인은 어디일 가능성이 큰가?
- 베이스 이미지 태그를 `17-jre` 로 두는 것과 `17.0.9_9-jre-alpine` 으로 두는 것의 차이는?

## 덧 — 흔한 오해

### "컨테이너를 쓰면 환경 문제가 전부 사라진다"

사라지는 것은 **이미지 안쪽** 환경 차이다. 바깥은 그대로 남는다.

```
이미지 안  : 런타임, 라이브러리, 파일 경로     → 고정된다
이미지 밖  : 커널 버전, CPU 아키텍처, 환경변수,
            마운트된 볼륨, 네트워크, 리소스 한도 → 여전히 다르다
```

맥에서 만든 이미지가 서버에서 `exec format error` 로 안 도는 일이 흔하다.
CPU 아키텍처가 다르기 때문이고, 이건 이미지 안쪽 문제가 아니다.

```visual
  - { from: 개발 PC, to: 레지스트리, label: push, note: "층 단위로 올라간다" }
  - { from: 레지스트리, to: 운영 서버, label: pull, note: "같은 다이제스트면 완전히 같은 파일이다" }
  - { from: 운영 서버, to: 운영 서버, label: run, note: "여기서 커널·아키텍처·환경변수·볼륨은 서버 것을 쓴다" }
  - { from: 운영 서버, to: 개발 PC, label: 그래도 다를 수 있음, note: "exec format error 는 이미지가 아니라 아키텍처 문제다" }
```

### "Dockerfile 이 곧 문서다"

반쯤 맞다. Dockerfile 은 **빌드 절차**를 적은 것이고, 실행에 필요한 것은 다 안 적혀 있다.
필요한 환경변수, 마운트해야 할 볼륨, 의존하는 외부 서비스는 밖에 있다.

```dockerfile file=Dockerfile bad label="이것만 보면 모른다"
FROM node:20-alpine
COPY . /app
CMD ["node", "/app/server.js"]
```

```yaml file=docker-compose.yml good label="실행 조건까지 적힌다"
services:
  app:
    build: .
    environment:
      DATABASE_URL: ${DATABASE_URL:?필수}
    depends_on: [db]
```

"어떻게 만드는가"와 "어떻게 돌리는가"는 다른 문서다. 둘 다 있어야 재현된다.

### "VM 을 쓰면 되지 않나"

VM 도 환경을 통째로 고정한다. 실제로 이미지(AMI 같은 것)를 만들어 배포하는 방식이 있다.

차이는 **비용**이다. VM 이미지는 수 GB 고 부팅에 수십 초가 걸린다.
코드 한 줄 고칠 때마다 그걸 만들고 올리고 띄우기에는 너무 무겁다.
컨테이너는 같은 발상을 **수십 MB 와 수백 ms** 로 끌어내렸다.
발상이 아니라 **비용이 바뀌어서** 쓰임새가 달라진 것이다.
