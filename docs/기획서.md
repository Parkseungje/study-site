# 개인 학습 커리큘럼 웹사이트 기획서

2026-10-03 · 박승제

> 원본은 [Claude 문서](https://claude.ai/code/artifact/f7d01b57-21fc-4515-9b09-82ad2a9bbce8)에 있다.
> 이 파일은 레포에 두는 사본이다. 원본을 고치면 이 파일도 다시 내보내야 한다.

## 배경과 문제의식

이 사이트가 푸는 문제는 하나다. 개념 설명을 읽다가 모르는 용어가 나와 학습이 끊기는 것.

실제 흐름은 이렇게 흘러간다. Spring을 배우려다 Dependency Injection을 모르고, DI를 찾다 IoC Container를 모르고, 거기서 다시 Bean을 만난다. 세 단계쯤 내려가면 원래 무엇을 배우려 했는지 잊는다.

기존 학습 수단은 각각 다른 이유로 이 문제를 못 푼다.

| 수단 | 한계 |
| --- | --- |
| 블로그 글 | 글마다 전제하는 지식 수준이 달라 어디서 시작할지 알 수 없다 |
| 공식 문서 | 이미 아는 사람 기준으로 쓰여 선행 지식을 명시하지 않는다 |
| 온라인 강의 | 순서는 있지만 모르는 용어가 나와도 그 자리에서 해소할 길이 없다 |
| 개인 노트 | 다시 볼 때 개념 사이의 연결이 남아 있지 않다 |

공통점은 "이 설명을 이해하려면 무엇을 먼저 알아야 하는가"가 어디에도 적혀 있지 않다는 점이다. 그 정보를 데이터로 갖는 것이 이 프로젝트의 핵심이다.

## 목표와 범위

사용자는 나 혼자다. 회사에서 쓰는 기술과 개인적으로 파는 기술을 쌓아두는 개인 학습 저장소다. 다중 사용자, 공유, 계정은 범위 밖이다.

달성하려는 것 네 가지:

1. **모르는 용어에서 바로 이동** — 본문 안 용어를 클릭하면 그 개념으로 가고, 언제든 돌아온다.
2. **책처럼 읽히는 상세 본문** — 목차가 있고, 절로 나뉘어지고, 순서대로 읽으면 끝까지 간다.
3. **그림으로 보는 동작** — 글로 설명하면 안 잡힐 것을 조작 가능한 그림으로 본다.
4. **빈 곳이 드러남** — 본문에서 참조했지만 아직 안 쓴 개념이 목록으로 남는다.

명시적으로 하지 않는 것:

- 강의처럼 완결된 콘텐츠를 쓰지 않는다. 내가 이해한 만큼만 짧게 적고 원문 링크를 남긴다.
- **진도 추적을 넣지 않는다.** 뭘 어디까지 봤는지는 기록하지 않는다.
- **복습 기능을 넣지 않는다.** 읽고 싶을 때 검색해서 다시 열면 된다.
- 코드 실행 환경을 넣지 않는다. 실습은 로컬 IDE에서 한다.
- 로그인, 권한, 공유 링크를 넣지 않는다.
- 모바일 전용 UI를 따로 만들지 않는다. 데스크톱 기준으로 만들고 반응형 정도만 챙긴다.
- 전체 개념을 한 화면에 펼치는 그래프 뷰를 1차 범위에 넣지 않는다. 링크를 타고 이동하는 것과는 다른 기능이다.

## 핵심 학습 모델

네 가지 장치를 둔다. 앞의 둘은 "무엇을 먼저 봐야 하는가"를 답하고, 뒤의 둘은 "본문 자체가 읽힐 만한가"를 답한다.

| 장치 | 막는 상황 | 학습자의 행동 |
| --- | --- | --- |
| 선행 요구사항 블록 | 페이지를 열자마자 전제 지식이 부족한 경우 | 진입 전에 되돌아가 선행 개념을 먼저 처리 |
| 3단계 난이도 | 설명이 너무 깊어 모르는 용어가 쌓이는 경우 | 입문 단계로 내려 읽고 나중에 올라옴 |
| 목차 있는 상세 본문 | 길어지면 어디까지 읽었는지 잊는 경우 | 목차로 위치를 보고 절 단위로 끊어 읽음 |
| 인터랙티브 시각 자료 | 글로만 읽어서는 동작이 안 그려지는 경우 | 그림을 직접 조작해보고 넘어감 |

### 선행 요구사항 블록

모든 개념 페이지 맨 위에 고정으로 놓인다. 각 항목은 내가 직접 체크하는 상태를 가진다.

- 전부 체크됨 → 바로 읽는다
- 하나라도 비었음 → 경고 배너 + 해당 개념으로 가는 링크

이게 다이어그램 아이디어가 진짜로 원했던 것을 대체한다. 전체 그래프를 보고 싶었던 게 아니라, 지금 이 페이지에 필요한 선행 개념만 알고 싶었던 것이다.

### 3단계 난이도

같은 개념을 세 번 쓴다. 분량이 늘어나는 게 아니라 독자가 달라진다.

| 단계 | 분량 | 전제하는 지식 | 내용 |
| --- | --- | --- | --- |
| 입문 | 3–5분 | 없음 | 한 줄 정의 + 코드 10줄 이내 |
| 중급 | 15–20분 | 입문 | 왜 이렇게 하는가, 안 쓰면 어떻게 되는가 |
| 심화 | 30분+ | 중급 + 선행 개념 | 내부 동작, 엣지 케이스 |

입문 단계는 전제 지식을 0으로 두는 게 규칙이다. 여기서 모르는 용어가 나오면 그건 글이 잘못 쓴 것이다.

### 책처럼 읽히는 상세 본문

본문은 짧을 필요가 없다. 길어도 구조가 보이면 읽힌다. 커리큘럼 전체도 책 목차처럼 보여준다. 개념이 장, 개념 안의 절이 소제목이다.

- 각 난이도 본문은 `##` 절로 나눈다. 절 제목이 곧 목차 항목이 된다.
- 목차는 사이드바에 고정되고, 스크롤하면 현재 절이 표시된다.
- 절 하나만 읽고 닫아도 되고, 링크로 그 절을 바로 열 수도 있다.

절 구성은 난이도마다 달라진다. 중급과 심화는 절이 5–10개까지 간다.

```markdown
## 직접 new 할 때 생기는 문제
## 주입의 세 가지 방식
## 생성자 주입을 권장하는 이유
## 순환 참조가 생길 때
```

이 목차는 저장 시에 본문에서 추출해둔다. 별도로 입력하지 않는다.

### 인터랙티브 시각 자료

그림은 코드로 만들지 않는다. 마크다운 안에 데이터만 적고, 렌더러가 `kind`별로 그린다.

개념마다 React 컴포넌트를 하나씩 써야 하면 60개는커녕 5개에서 멈춘다. 컴포넌트는 네 개만 만들어두고 재사용한다.

| kind | 쓰는 곳 | 조작 |
| --- | --- | --- |
| `step` | 순서가 있는 과정 | 단계를 누르면 그 시점 상태가 보임 |
| `sequence` | 둘 이상이 주고받는 것 | 메시지를 하나씩 진행 |
| `structure` | 트리·박스 구조 | 노드 호버하면 설명 |
| `playground` | 입력에 따라 결과가 바뀌는 것 | 값을 고르면 결과가 바뀜 |

순서가 있는 과정은 `step`으로 쓴다.

```yaml
id: bean-lifecycle
kind: step
title: Bean은 다섯 단계를 거쳐 사용 가능해진다
steps:
  - name: 인스턴스화
    detail: 생성자 호출. 아직 의존성은 비어 있다
    code: new UserService()
  - name: 의존성 주입
    detail: "@Autowired 대상이 채워진다"
  - name: 초기화 콜백
    detail: "@PostConstruct 실행"
```

주고받는 것은 `sequence`다.

```yaml
id: tcp-handshake
kind: sequence
actors: [클라이언트, 서버]
messages:
  - { from: 클라이언트, to: 서버, label: SYN, note: "seq=x" }
  - { from: 서버, to: 클라이언트, label: SYN+ACK, note: "ack=x+1" }
  - { from: 클라이언트, to: 서버, label: ACK }
```

`playground`는 임의의 코드를 실행하지 않는다. 조건과 결과를 표로 선언한다. 그래야 AI도 쓸 수 있고 안전하다.

```yaml
id: cache-control
kind: playground
inputs:
  - { name: directive, type: select, options: [no-store, no-cache, "max-age=60"] }
outcomes:
  - { when: "no-store",   result: "매 요청 서버로. 캐시에 저장 안 함" }
  - { when: "no-cache",   result: "캐시에 저장하되 매번 재검증" }
  - { when: "max-age=60", result: "60초간 서버에 묻지 않음" }
```

블록은 본문의 `visual` 펜스 안에 적는다. 써놓은 자리에 그대로 렌더링된다. import가 YAML을 파싱해 `concept_visual.spec`에 넣고, 원본은 마크다운에 남는다.

#### 그리게 만드는 장치

선언형으로 두는 진짜 이유는 작성 비용이다. 세 군데서 밀어낸다.

| 지점 | 장치 |
| --- | --- |
| 쓸 때 | 프롬프트 템플릿이 "그림이 설명보다 빠른 곳은 visual 블록으로 낼 것"을 항상 포함 |
| 넣을 때 | import 검증이 "중급 본문에 visual 0개" 경고 |
| 볼 때 | "시각자료 없는 개념" 목록 화면 |

AI는 필드가 정해진 YAML을 잘 뽑는다. `kind`가 네 개로 고정되어 있으면 거의 매번 맞게 나온다. 내가 그림을 그리는 게 아니라 템플릿이 데이터를 요구하고 렌더러가 그린다.

대가는 표현력이다. B-Tree 분할 애니메이션 같은 건 네 종류로 안 된다. 그런 건 `kind: custom`으로 빠져나가 컴포넌트를 직접 쓰되, 예외로만 둔다. 60개 개념에 쓸 만한 그림이 붙는 게, 5개에 완벽한 그림이 붙는 것보다 낫다.

### 코드 예제

기술 개념 설명의 절반은 코드다. 그냥 코드 블록을 넣는 것과 읽힐 수 있게 넣는 것은 다르다.

| 요소 | 동작 | 왜 |
| --- | --- | --- |
| 파일명 헤더 | 블록 위에 `UserService.java` 표시 | 이 코드가 어디 들어가는지 |
| 나쁜 예 → 좋은 예 | 두 블록을 나란히 놓고 라벨 붙임 | DI 같은 개념은 비교로 이해됨 |
| 강조 줄 | 특정 줄에 배경색 + 오른쪽 주석 | 긴 코드에서 볼 곳을 집음 |
| 접기 | 20줄 넘으면 기본 접힘 | 전체 맥락은 필요하지만 매번 다 볼 필요는 없음 |
| 복사 버튼 | 클립보드로 | IDE로 옮겨 실습 |

별도 문법을 만들지 않는다. 마크다운 코드 펜스의 언어 자리에 메타를 이어 붙인다.

`java file=UserService.java bad label="직접 생성" highlight=2-4`

| 메타 | 뜻 |
| --- | --- |
| `file=` | 블록 위에 표시할 파일명 |
| `bad` / `good` | 비교 쌍의 어느 쪽인지 |
| `label=` | 비교 블록 위에 붙는 짧은 설명 |
| `highlight=` | 강조할 줄 번호 범위 |
| `fold` | 기본 접기 |

`bad`와 `good`이 연속해서 나오면 렌더러가 좌우로 붙여준다. 화면이 좁으면 위아래로 내려간다. 메타가 없으면 평범한 코드 블록으로 그냥 렌더링된다.

## 데이터 모델

계층은 세 단계다. 트랙이 책, 장이 챕터, 개념이 절에 해당한다.

```
backend (트랙)
└─ Spring (장)
   ├─ Dependency Injection (개념)
   ├─ IoC Container
   ├─ Bean 생명주기
   └─ AOP
```

장이 없으면 backend 트랙에 개념 60개가 평평하게 나열된다. 그건 목차가 아니라 목록이다. 선행 관계로 정렬하면 순서는 나오지만 묶음은 안 나온다.

핵심 엔티티는 여전히 개념(Concept)이다. 용어 미리보기는 별도 테이블이 아니라 개념의 `summary` 필드를 재사용한다.

```json
{
  "id": "spring-di",
  "title": "Dependency Injection",
  "chapterId": "spring",
  "ord": 2,
  "summary": "객체가 필요한 의존성을 직접 생성하지 않고 외부에서 받는 방식",
  "versionNote": "Spring Boot 3.2 기준",
  "levels": {
    "intro":    { "body": "...", "minutes": 5 },
    "standard": { "body": "## 직접 new 할 때...", "minutes": 20 },
    "deep":     { "body": "...", "minutes": 40 }
  },
  "edges": [
    { "to": "java-interface", "type": "prerequisite" },
    { "to": "spring-ioc",     "type": "deepens" },
    { "to": "test-mocking",   "type": "related" }
  ],
  "visuals": [
    { "id": "di-three-ways", "kind": "step", "title": "주입 세 방식 비교" }
  ],
  "sources": [
    { "label": "Spring 공식 문서", "url": "https://docs.spring.io/..." }
  ],
  "updatedAt": "2026-10-03"
}
```

`ord`는 장 안에서의 순서다. 선행 관계와 따로 둔다. 선행 관계는 장을 넘어 걸리기도 하고(Spring의 DI가 Java의 Interface를 요구), 그걸로 전체 순서를 정하려면 내가 읽고 싶은 순서와 어긋난다. 목차 순서는 내가 정하고, 선행 관계는 경고만 띄운다.

관계는 세 타입만 둔다. 타입을 늘리면 입력할 때 고민하게 되고, 고민하면 안 적게 된다.

| 타입 | 의미 | 화면에서 쓰이는 곳 | 방향 |
| --- | --- | --- | --- |
| `prerequisite` | 이걸 모르면 이 페이지를 못 읽는다 | 상단 선행 요구사항 블록 | 단방향 |
| `deepens` | 이 개념의 다음 단계 | 페이지 하단 "더 들어가기" | 단방향 |
| `related` | 같이 알면 좋은 것 | 사이드바 | 양방향 |

구현상 주의점 두 가지:

- `prerequisite`는 순환하면 안 된다. A가 B를, B가 A를 선행으로 가리키면 어디서도 시작할 수 없다. 저장 시 순환 검사를 넣는다.
- `related`는 한쪽에만 써도 양쪽 화면에 나오게 한다. 두 번 입력하지 않아도 되게.

### 프롬프트 템플릿

새 개념을 추가할 때 AI에게 보낼 프롬프트를 사이트에 저장해둔다. 매번 "3단계로 나눠서, 선행 개념 명시해서, 요약 한 줄 붙여서"를 다시 설명하지 않기 위해서다.

```json
{
  "id": "add-concept-ko",
  "name": "개념 추가 · 기본",
  "body": "{{title}} 개념을 아래 형식의 JSON으로만 써줘. 설명 문장 붙이지 말 것. 본문은 전부 한국어.\n- chapterId는 {{chapterId}} 고정\n- summary: 한 문장 정의\n- versionNote: 기준 버전 명시\n- intro: 전제 지식 0 기준, 5분, 절 나누지 않음\n- standard: 20분, ## 절 5개 이상\n- deep: 40분, ## 절로 나누고 내부 동작과 엣지 케이스\n- 절 제목은 그대로 목차가 되니 내용을 드러내게 쓸 것\n- 코드는 펜스에 file= 붙이고, 비교가 될 때는 bad/good 쌍으로\n- edges: prerequisite / deepens / related\n- 본문 안 다른 개념은 [[id]]로 표기\n- 그림이 설명보다 빠른 곳은 :::visual <id>::: 로 자리를 잡고 visuals에 kind(step|sequence|structure|playground)와 묘사를 같이 냄\n기존 개념 id 목록: {{existingIds}}",
  "variables": ["title", "chapterId", "existingIds"],
  "updatedAt": "2026-10-03"
}
```

`{{existingIds}}`는 사이트가 현재 DB의 개념 id를 넣어 치환한다. 이게 있어야 AI가 없는 id를 지어내지 않고 기존 개념에 연결한다. "설명 문장 붙이지 말 것"을 넣는 이유는 받은 응답을 그대로 붙여넣기 위해서다.

템플릿은 여러 개 둔다. 개념 추가용, 기존 개념 심화 보강용, 용어 요약 재생성용으로 나누면 쓰기 편하다.

## 화면 및 기능 명세

화면은 여섯 개다. 전부 읽기 전용이다. 쓰는 것은 마크다운 파일에서 하고 import로 올린다.

| 화면 | 구성 | 핵심 동작 |
| --- | --- | --- |
| 트랙 목록 | 트랙 카드 + 각 트랙의 장·개념 수 | 트랙 클릭 → 커리큘럼 |
| 커리큘럼 | 책 목차 형식. 장 → 개념 → 절 3단계 | 장 접기/펼치기, 절 클릭 → 그 위치로 |
| 개념 상세 | 선행 블록 → 난이도 탭 → 목차 + 본문 → 더 들어가기 → 원문 링크 | 난이도 전환, 링크 이동, 시각 자료 조작 |
| 검색 | 제목 + 요약 + 본문 + 절 제목 대상 | 단축키로 열고 바로 이동 |
| 프롬프트 템플릿 | 템플릿 목록 + 개념명·장 입력란 | 치환된 전문 복사 → AI에 붙여넣기 |
| 비어 있는 개념 | `[[id]]`로 참조됐지만 파일이 없는 목록 | 클릭 → 그 id로 템플릿 바로 열기 |

### 개념 상세 화면

가장 중요한 화면이라 순서를 고정한다.

1. **선행 요구사항 블록** — 본문보다 위. 내려야 보이면 없는 것과 같다.
2. **난이도 탭** — 입문 / 중급 / 심화. 기본값은 입문.
3. **목차 사이드바** — 본문 절 목록, 현재 위치 표시. 난이도를 바꾸면 목차도 같이 바뀐다.
4. **본문** — 마크다운 렌더링, 코드 블록 신택 하이라이트, 용어 하이퍼링크, 시각 자료 블록.
5. **더 들어가기** — `deepens` 관계 개념 링크.
6. **내 메모** — 해당 개념에 남기는 한줄짜리 기록.

### 용어 마크 방식

본문을 쓸 때 개념 id를 직접 링크로 박는다. 별도 에디터 없이 마크다운으로 끝낸다.

```markdown
Spring은 [[spring-di]]을 통해 객체를 연결한다.
```

렌더링 시 `[[spring-di]]`는 해당 개념의 `title`을 텍스트로 가진 하이퍼링크가 된다. 클릭하면 그 개념으로 이동하고, 호버하면 `summary` 한 줄이 미리보기로 뜬다. 미리보기만으로 충분할 때는 안 넘어가고, 부족하면 넘어가면 된다. 어느 쪽이든 돌아올 길은 남는다.

존재하지 않는 id는 빨간색으로 표시해서 "아직 안 썼음"을 드러낸다. 이게 다음에 써야 할 개념 목록 역할을 한다.

### 링크 이동과 돌아오기

링크를 타고 개념 사이를 옮겨다니는 것은 Phase 1에 들어간다. 단, 돌아올 길이 없으면 그게 바로 rabbit hole이 된다.

- 방문 경로를 스택으로 쌓고, 상단에 브레드크럼으로 보여준다. `Spring › DI › IoC Container`
- 스택의 아무 지점이나 클릭하면 거기로 돌아간다.
- 브라우저 뒤로가기와 스택을 똑같이 동작시킨다.

이 세 줄이 "원래 뭘 보려 했는지 잊는" 문제를 막는다. 전체 그래프 뷰는 여전히 Phase 3이다. 둘은 다른 기능이다.

### 개념 추가 흐름

프롬프트 템플릿의 나머지 반쪽이다. 다만 화면이 아니라 **파일 → import 스크립트**로 처리한다. 본문 원본이 마크다운이라 사이트에 편집 화면을 만들 이유가 없다.

개념 하나를 추가하는 흐름은 네 단계다.

1. **템플릿 복사** — 사이트의 템플릿 화면에서 개념명과 장을 고르면 `{{title}}`, `{{chapterId}}`, `{{existingIds}}`가 치환된 전문이 나온다.
2. **파일 저장** — AI가 준 마크다운을 `content/<chapterId>/<id>.md`로 저장한다.
3. **import** — `npm run import`. 프런트매터와 `##` 절을 파싱해 upsert하고 `concept_section`을 다시 만든다.
4. **검증 출력** — 오류면 멈추고, 경고면 진행하고 목록을 찍는다.

검증은 두 등급으로 나눈다. 오류는 저장을 막고, 경고는 막지 않는다.

| 등급 | 검사 | 예 |
| --- | --- | --- |
| 오류 | 필수 필드 누락 | `summary`가 없음 |
| 오류 | `chapterId`가 존재하지 않음 | 장을 먼저 만들거나 골라야 함 |
| 오류 | `edges`의 `to`가 없는 개념 | 오타이거나 AI가 지어냄 |
| 오류 | `prerequisite` 순환 발생 | A→B→A가 되면 어디서도 시작 못 함 |
| 오류 | `:::visual <id>:::`가 `visuals`에 없는 id | 본문에 빈 자리만 남음 |
| 경고 | 본문의 `[[id]]`가 없는 개념 | 아직 안 썼을 뿐일 수 있음. 빨간 링크로 남김 |
| 경고 | `standard`에 `##` 절이 3개 미만 | 책처럼 읽히기에 얄긂 |
| 경고 | `versionNote`가 비어 있음 | 나중에 기준 버전을 모르게 됨 |

빈 링크 경고가 오류가 아닌 것이 중요하다. 없는 개념을 가리키는 링크는 막을 대상이 아니라 다음에 써야 할 목록이다.

## 기술 스택과 아키텍처

전체를 Docker로 띄우고 GitHub로 형상관리한다. 백엔드를 두는 이유는 편집 UI 때문이다. 개념을 추가할 때마다 파일을 고쳐 커밋하는 것은 회사 일하다 떠올린 개념을 적는 흐름을 끊는다.

| 레이어 | 선택 | 근거 |
| --- | --- | --- |
| 프론트 | Next.js (App Router) + TypeScript | 라우팅·서버 렌더링 내장, API Route로 백엔드까지 한 프로젝트 |
| 본문 원본 | 레포의 `content/*.md` | git 이력이 남고, AI에게 받은 걸 파일로 저장하면 끝 |
| DB | MySQL 8 + Prisma | 관계 쿼리 필요, 컨테이너로 띄우면 설치 부담 없음 |
| import | `scripts/import.ts` | `content/`를 읽어 upsert, 절과 링크 검증 |
| 실행 환경 | Docker Compose (db) + 로컬 `npm run dev` | 개발 중 핫리로드 살리려고 앱은 컨테이너 밖 |
| 형상관리 | GitHub (private repo) | 본문·스키마·코드를 한 레포에 |

### Docker 구성

컨테이너 두 개만 둔다. 개인용이라 리버스 프록시나 별도 캐시는 넣지 않는다.

```yaml
services:
  db:
    image: mysql:8
    command: --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
    environment:
      MYSQL_DATABASE: study
      MYSQL_USER: study
      MYSQL_PASSWORD: study
      MYSQL_ROOT_PASSWORD: root
    ports:
      - "3307:3306"
    volumes:
      - mysql-data:/var/lib/mysql
      - ./docker/init:/docker-entrypoint-initdb.d:ro

volumes:
  mysql-data:
```

`utf8mb4`는 선택이 아니라 필수다. 본문이 한글이고 이모지나 특수문자가 섞여도 깨지면 안 된다.

호스트 포트가 3307인 이유는 로컬에 이미 MySQL이 3306을 쓰고 있어서다.

데이터는 컨테이너 안이라 GitHub에 안 올라간다. 백업은 `mysqldump`를 주기적으로 돌려 `backup/` 폴더에 남기고, 그 파일만 커밋한다. 개인 학습 기록이라 용량이 클 일은 없다.

### 테이블 구성

모든 테이블과 컬럼에 한글 코멘트를 달아둔다. 나중에 DB를 직접 열어봤을 때 컬럼명만 보고 다시 추측하지 않기 위해서다.

Prisma는 DB 레벨 COMMENT를 표현하지 못하므로, 마이그레이션 SQL에 직접 적는다. 스키마를 바꿀 때마다 새 마이그레이션 SQL에도 COMMENT를 같이 적어야 한다.

```sql
CREATE TABLE track (
  id     VARCHAR(50)  NOT NULL COMMENT '트랙 식별자 (backend, frontend, infra)',
  title  VARCHAR(100) NOT NULL COMMENT '화면에 보이는 트랙명',
  ord    SMALLINT     NOT NULL COMMENT '목록 노출 순서',
  PRIMARY KEY (id)
) COMMENT='최상위 분류, 책 한 권에 해당';

CREATE TABLE chapter (
  id        VARCHAR(64)  NOT NULL COMMENT '장 식별자 (spring, jpa, kafka)',
  track_id  VARCHAR(50)  NOT NULL COMMENT '소속 트랙 FK',
  title     VARCHAR(100) NOT NULL COMMENT '장 제목',
  summary   VARCHAR(300) NOT NULL COMMENT '이 장에서 무엇을 다루는지 한 줄',
  ord       SMALLINT     NOT NULL COMMENT '트랙 안에서의 순서',
  PRIMARY KEY (id)
) COMMENT='개념을 묶는 장, 책의 챕터에 해당';

CREATE TABLE concept (
  id            VARCHAR(64)  NOT NULL COMMENT '개념 식별자, [[id]] 표기에 쓰임',
  chapter_id    VARCHAR(64)  NOT NULL COMMENT '소속 장 FK',
  title         VARCHAR(200) NOT NULL COMMENT '화면에 보이는 개념명',
  summary       VARCHAR(500) NOT NULL COMMENT '한 문장 요약, 링크 미리보기에 그대로 쓰임',
  version_note  VARCHAR(100) NULL     COMMENT '기준 버전, 예: Spring Boot 3.2',
  ord           SMALLINT     NOT NULL COMMENT '장 안에서의 순서',
  updated_at    DATETIME     NOT NULL COMMENT '마지막 수정 시각',
  PRIMARY KEY (id)
) COMMENT='학습 개념 본문의 상위 정보';

CREATE TABLE concept_level (
  concept_id  VARCHAR(64) NOT NULL COMMENT '개념 FK',
  level       ENUM('intro','standard','deep') NOT NULL COMMENT '난이도 단계',
  body        MEDIUMTEXT  NOT NULL COMMENT '마크다운 본문, [[id]] 링크와 visual 펜스 포함',
  minutes     SMALLINT    NOT NULL COMMENT '예상 읽기 시간(분)',
  PRIMARY KEY (concept_id, level)
) COMMENT='개념별 3단계 본문';

CREATE TABLE concept_section (
  concept_id  VARCHAR(64)  NOT NULL COMMENT '개념 FK',
  level       ENUM('intro','standard','deep') NOT NULL COMMENT '난이도 단계',
  ord         SMALLINT     NOT NULL COMMENT '본문 안 절 순서',
  heading     VARCHAR(200) NOT NULL COMMENT '절 제목, 목차에 그대로 표시',
  anchor      VARCHAR(100) NOT NULL COMMENT 'URL 앵커, 절로 바로 이동할 때 쓰임',
  PRIMARY KEY (concept_id, level, ord)
) COMMENT='본문에서 추출한 목차, import 가 재생성';

CREATE TABLE edge (
  from_id  VARCHAR(64) NOT NULL COMMENT '출발 개념',
  to_id    VARCHAR(64) NOT NULL COMMENT '도착 개념',
  type     ENUM('prerequisite','deepens','related') NOT NULL COMMENT '관계 종류',
  PRIMARY KEY (from_id, to_id, type)
) COMMENT='개념 간 관계';

CREATE TABLE concept_visual (
  id          VARCHAR(64)  NOT NULL COMMENT '시각 자료 식별자, YAML 의 id 값',
  concept_id  VARCHAR(64)  NOT NULL COMMENT '소속 개념 FK',
  level       ENUM('intro','standard','deep') NOT NULL COMMENT '어느 난이도 본문에 들어가는지',
  title       VARCHAR(200) NOT NULL COMMENT '그림 제목, YAML 의 title',
  kind        ENUM('step','sequence','structure','playground','custom') NOT NULL COMMENT '렌더러가 고를 컴포넌트 종류',
  spec        JSON         NOT NULL COMMENT '마크다운 visual 블록의 YAML 을 파싱한 값',
  ord         SMALLINT     NOT NULL COMMENT '본문 안 등장 순서',
  PRIMARY KEY (id)
) COMMENT='본문에 끼우는 조작 가능한 그림, import 가 재생성';

CREATE TABLE prompt_template (
  id          VARCHAR(64)  NOT NULL COMMENT '템플릿 식별자',
  name        VARCHAR(100) NOT NULL COMMENT '목록에 보이는 이름',
  body        TEXT         NOT NULL COMMENT '프롬프트 본문, {{변수}} 포함',
  updated_at  DATETIME     NOT NULL COMMENT '마지막 수정 시각',
  PRIMARY KEY (id)
) COMMENT='개념 추가용 AI 프롬프트 템플릿';

CREATE TABLE note (
  concept_id  VARCHAR(64)  NOT NULL COMMENT '개념 FK',
  body        VARCHAR(500) NOT NULL COMMENT '내가 남긴 한줄 메모',
  updated_at  DATETIME     NOT NULL COMMENT '마지막 수정 시각',
  PRIMARY KEY (concept_id)
) COMMENT='개념별 개인 메모';

CREATE TABLE source (
  id          BIGINT AUTO_INCREMENT NOT NULL COMMENT '일련번호',
  concept_id  VARCHAR(64)  NOT NULL COMMENT '개념 FK',
  label       VARCHAR(200) NOT NULL COMMENT '출처 이름',
  url         VARCHAR(500) NOT NULL COMMENT '원문 주소',
  PRIMARY KEY (id)
) COMMENT='개념별 원문 링크';
```

`concept_section`과 `concept_visual`은 손으로 넣지 않는다. import가 마크다운을 읽으면서 `##` 줄과 `visual` 펜스를 파싱해 해당 개념의 행을 전부 지우고 다시 넣는다. 본문과 둘이 어긋나는 경우를 없애려고 이렇게 한다.

`edge`는 복합 PK로 중복을 막고, 저장 시 `prerequisite` 순환 검사를 애플리케이션 레벨에서 한다.

## 개발 로드맵

링크를 타고 개념 사이를 옮겨다니는 것은 Phase 1에 들어가지만, 전체를 한 화면에 펼치는 그래프 뷰는 Phase 3으로 미룬다. 개념이 15개일 때 그린 그래프는 정보가 없고, 50개가 넘어가야 비로소 "전체가 안 보인다"는 문제가 생긴다. 그 문제가 실제로 생기기 전에는 만들지 않는다.

| | Phase 1 · MVP | Phase 2 · 확장 | Phase 3 · 선택 |
| --- | --- | --- | --- |
| 내용 | 트랙 › 장 › 개념 + 3단계 본문<br>선행 블록 + 코드 비교 블록<br>JSON 붙여넣기 + 검증<br>목차 사이드바 + 링크 이동 | 인터랙티브 시각 자료<br>전문 검색 + 빈 링크 리포트<br>개념별 메모 + 백업 덤프<br>템플릿 여러 개 관리 | 관계 그래프 뷰<br>트랙 단위로만 표시<br>링크 이동과는 별개 기능 |
| 산출물 | Docker 기동, 개념 15개 | 트랙 3개, 개념 60개 | 게이트 못 넘으면 안 만든다 |
| 다음 단계 게이트 | 2주 써보고 끊김이 줄었나 | 개념 50개 넘고 구조가 안 보일 때 | — |

Phase 1에서 검증할 것은 기능의 완성도가 아니라 **학습이 덜 끊기는가** 하나다. 개념 15개를 넣고 2주를 써본 다음, 이전처럼 다른 탭을 열게 되는지를 본다. 그런다면 선행 요구사항이나 입문 단계가 제 역할을 못 하고 있는 것이고, 기능을 더 붙이기 전에 그걸 고쳐야 한다.

Phase 2는 개념이 늘어나면서 생기는 관리 문제를 다룬다. 특히 빈 링크 리포트가 중요하다. 본문에 `[[kafka-consumer-group]]`을 썼는데 그 개념이 없다면, 그게 다음에 프롬프트 템플릿에 넣어서 채워야 할 개념이다.

## 정해진 것

착수 전에 막혔던 것들은 정리됐다.

| 결정 | 내용 |
| --- | --- |
| 레포 위치 | `C:\develop\study-site`. 기존 `study` 안에 두면 git 레포가 중첩된다 |
| 본문 원본 | 레포의 `content/` 마크다운. 파일 하나가 개념 하나 |
| 기존 자료 | `java-fundamentals`, `spring-fundamentals`의 문서 88개는 쓰지 않는다. 새로 쓴다 |
| DB 역할 | 원본이 아니라 조회용. `content/`를 import해서 채운다 |
| 개발 중 실행 | DB만 컨테이너, 앱은 로컬 `npm run dev`. 앱 컨테이너화는 나중 |

마크다운을 원본으로 두면 편집 UI가 가벼워진다. AI에게 받은 본문을 파일로 저장하고 import하면 끝이라, 사이트 안에 에디터를 만들 일이 없다. 검증은 화면이 아니라 import 스크립트가 한다.
