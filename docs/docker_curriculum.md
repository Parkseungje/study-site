# 📚 PART 1 — 배포의 고통과 격리의 역사

> **목표**: "컨테이너가 왜 필요한가"에 직접 답한다. VM 과의 차이를 커널 수준에서 구분한다.

## 1.1 "내 PC에선 되는데" (왜 컨테이너가 등장했나)

**로우레벨의 불편함**: 애플리케이션은 코드만으로 돌지 않는다. 런타임 버전, 시스템 라이브러리,
환경변수, 파일 경로, OS 패치 수준이 전부 맞아야 한다. 개발 PC·테스트 서버·운영 서버가
조금씩 다르면 **같은 코드가 다르게 동작한다.** 설치 절차서를 아무리 잘 써도
"그 서버에만 있던 라이브러리"는 문서에 안 적힌다.

**해결**: 코드가 아니라 **실행에 필요한 파일 전부를 한 덩어리로 묶어** 옮긴다.
그 덩어리가 이미지다. 어디서 풀어도 같은 파일 구성이 나오므로 환경 차이가 사라진다.

- 설정 관리 도구(Ansible, Chef)는 "같은 절차를 재현"하려 했다. 절차는 같아도 **출발 상태가 다르면 결과가 다르다.**
- 이미지는 절차가 아니라 **결과물**을 고정한다. 이 차이가 핵심이다.

**자기 점검**
- 설치 스크립트를 완벽하게 써도 환경 차이가 남는 이유는?
- 이미지가 "절차가 아니라 결과를 고정한다"는 말은 무슨 뜻인가?

## 1.2 격리의 역사 — chroot 에서 cgroup 까지

**로우레벨의 불편함**: 한 호스트에서 프로세스를 나눠 돌리려는 시도는 오래됐다.
`chroot`(1979)는 **파일 시스템 루트만** 바꾼다. 프로세스 목록, 네트워크, 사용자는 그대로 공유된다.
루트 권한이 있으면 빠져나가는 방법도 알려져 있다.

**중간**: FreeBSD jail(2000)과 Solaris Zones(2004)가 프로세스·네트워크까지 격리했다.
리눅스에서는 namespace 가 2002년부터 종류별로 하나씩 들어왔고, cgroup 은 2008년에 합류했다.
LXC 가 이것들을 묶어 "리눅스 컨테이너"를 만들었다.

**해결**: Docker(2013)는 **새 격리 기술을 만들지 않았다.**
이미 있던 커널 기능 위에 **이미지 포맷과 배포 방법**을 얹었다.

- 기술적 혁신이 아니라 **사용성의 혁신**이었다. 그래서 빨리 퍼졌다
- LXC 는 "가벼운 VM"에 가까웠고, Docker 는 "앱 하나를 담는 상자"로 방향을 틀었다

**자기 점검**
- `chroot` 만으로 부족한 이유를 세 가지 이상 들면?
- Docker 가 커널 기능을 만들지 않았는데도 판을 바꾼 이유는?

## 1.3 물리 서버 → VM → 컨테이너

**로우레벨의 불편함**: 앱 하나에 서버 한 대를 쓰면 안전하지만 낭비가 크다.
한 대에 여러 앱을 올리면 **포트가 겹치고, 라이브러리 버전이 충돌하고, 하나가 죽으면 같이 죽는다.**

**중간**: 하이퍼바이저로 **가상 머신**을 띄운다. 격리는 완벽하다. 대신 VM 마다
**게스트 OS 를 통째로** 올려야 해서 수 GB 와 수십 초가 든다.

**해결**: 컨테이너는 **호스트 커널을 공유**하고 파일 시스템과 네트워크만 분리한다.
OS 가 하나뿐이라 수십 MB 와 수백 ms 로 끝난다.

```
VM         : [앱][게스트OS] [앱][게스트OS]  ← OS 가 여러 벌
           : ────── 하이퍼바이저 ──────
컨테이너    : [앱]      [앱]      [앱]       ← 프로세스일 뿐
           : ────── 호스트 커널 ──────
```

**자기 점검**
- VM 이 컨테이너보다 느리고 무거운 **구조적 이유**는?
- 리눅스 컨테이너를 Windows 에서 돌리려면 무엇이 더 필요한가? 왜인가?

## 1.4 컨테이너는 가상 머신이 아니다

**로우레벨의 불편함**: 컨테이너를 "가벼운 VM"으로 이해하면 반드시 틀린 판단을 한다.
안에 systemd 를 띄우려 하고, SSH 를 열고, 여러 프로세스를 담는다.

**해결**: 컨테이너는 **격리된 프로세스 하나**다. 호스트에서 `ps` 를 치면 그 프로세스가 그대로 보인다.
PID 만 다르다.

- 그래서 "한 컨테이너 한 프로세스"가 원칙이다. 로그도 파일이 아니라 stdout 으로 낸다
- 커널을 공유하므로 **커널 취약점은 격리를 뚫는다.** VM 보다 격리 강도가 약하다
- 강한 격리가 필요하면 Firecracker·Kata 같은 **경량 VM** 을 쓴다. 클라우드의 서버리스가 그 방식이다

**자기 점검**
- 컨테이너 안에서 `ps` 를 치면 프로세스가 한두 개뿐인데, 호스트에서는 왜 보이는가?
- 멀티 테넌트 환경에서 컨테이너만으로 격리하면 위험한 이유는?

# 📚 PART 2 — 컨테이너 런타임의 실체

> **목표**: `docker run` 한 줄 뒤에서 무엇이 도는지 안다. "Docker = 컨테이너"라는 오해를 깬다.

## 2.1 docker run 을 치면 무슨 일이 일어나는가

**로우레벨의 불편함**: `docker` 를 하나의 프로그램으로 알면
데몬이 죽었을 때, 컨테이너만 남았을 때, Docker 를 안 쓰는 환경에서 무슨 일인지 설명을 못 한다.

**해결**: Docker 는 **여러 층으로 나뉜 구조**다.

```
docker CLI          내가 치는 명령. REST API 로 보낸다
    ↓
dockerd             이미지 빌드, 네트워크, 볼륨 관리
    ↓
containerd          컨테이너 생명주기 관리. 이미지 pull 도 여기
    ↓
containerd-shim     컨테이너마다 하나. 부모 역할을 맡는다
    ↓
runc                namespace·cgroup 을 설정하고 프로세스를 띄운 뒤 빠진다
    ↓
리눅스 커널
```

- `runc` 는 **컨테이너를 만들고 끝난다.** 계속 떠 있지 않다
- `shim` 이 남아 부모 노릇을 한다. 그래서 **dockerd 를 재시작해도 컨테이너는 안 죽는다**

**자기 점검**
- `dockerd` 를 재시작했는데 컨테이너가 살아 있는 이유는?
- `runc` 가 떠 있지 않은데 컨테이너가 도는 것은 모순 아닌가?

## 2.2 OCI 표준 — 이미지와 런타임의 규격

**로우레벨의 불편함**: Docker 가 사실상 표준이 되자 **한 회사 포맷에 묶인다**는 우려가 커졌다.
다른 구현이 나와도 이미지가 호환되지 않으면 쓸 수 없다.

**해결**: 2015년 **OCI(Open Container Initiative)** 가 규격을 문서로 떼어냈다.

| 규격 | 정하는 것 |
|---|---|
| image-spec | 이미지가 어떤 파일 구조인가 (manifest, config, layer) |
| runtime-spec | 번들을 어떻게 실행하는가 (namespace, cgroup 설정) |
| distribution-spec | 레지스트리와 어떻게 주고받는가 |

- Docker 는 `libcontainer` 를 기부했고 그것이 `runc` 가 됐다
- 그래서 **Docker 로 만든 이미지를 podman 이 돌리고, 그 반대도 된다**

**자기 점검**
- 이미지가 표준이라는 사실이 실무에 어떤 자유를 주는가?
- 규격이 세 개로 나뉜 이유는?

## 2.3 Docker 없이도 컨테이너는 돈다

**로우레벨의 불편함**: `dockerd` 는 **루트로 도는 상주 데몬**이다.
그 소켓에 접근할 수 있으면 사실상 호스트 루트다. CI 서버에서 특히 문제가 된다.

**해결**: 데몬 없는 구현이 나왔다.

| 도구 | 성격 |
|---|---|
| `podman` | 데몬 없음. 사용자 권한으로 실행(rootless). CLI 가 docker 와 거의 같다 |
| `nerdctl` | containerd 를 직접 쓰는 CLI |
| `CRI-O` | Kubernetes 전용으로 최소 기능만 |
| `buildah` | 빌드 전용. 데몬 없이 이미지를 만든다 |

- `alias docker=podman` 으로 대체되는 경우가 많다
- 개발 머신은 Docker Desktop 이 편하고, CI·서버는 데몬 없는 쪽이 안전하다

**자기 점검**
- 데몬이 루트로 도는 것이 왜 보안 문제인가?
- CI 환경에서 podman 이나 buildah 를 고르는 이유는?

## 2.4 Kubernetes 가 dockershim 을 버린 이유

**로우레벨의 불편함**: Kubernetes 는 런타임과 **CRI(Container Runtime Interface)** 로 대화한다.
그런데 Docker 는 CRI 를 말하지 못했다. K8s 가 **dockershim 이라는 번역기**를 자기 코드에 들고 있었다.

```
kubelet → dockershim → dockerd → containerd → runc   (예전)
kubelet → containerd → runc                          (지금)
```

**해결**: Kubernetes 1.24(2022)에서 dockershim 을 제거했다.
Docker 안에 이미 containerd 가 있으니 **중간을 걷어낸 것**이다.

- "Docker 지원 중단"으로 와전됐지만, **Docker 로 만든 이미지는 그대로 돈다.** OCI 표준이라서다
- 바뀐 것은 노드에서 돌던 런타임뿐이다

**자기 점검**
- "K8s가 Docker를 버렸다"는 말이 왜 부정확한가?
- 이미지 호환성과 런타임 호환성은 어떻게 다른가?

# 📚 PART 3 — 이미지와 레이어

> **목표**: 이미지가 왜 층으로 되어 있는지 이해하고, 빌드 속도와 용량을 그 구조로 설명한다.

## 3.1 이미지는 무엇을 담는가

**로우레벨의 불편함**: 앱을 통째로 묶으면 배포할 때마다 전체를 다시 전송해야 한다.
코드 한 줄 고쳤는데 1GB 를 다시 올린다.

**해결**: 이미지를 **읽기 전용 층(layer)** 으로 쌓는다. Dockerfile 의 한 명령이 한 층이고,
그 명령이 **바꾼 파일만** 층에 담긴다. 바뀐 층만 전송하면 된다.

- 이미지 = 읽기 전용 층들 + 메타데이터(실행 명령, 환경변수, 노출 포트)
- 같은 베이스를 쓰는 이미지 열 개가 있어도 **디스크에는 베이스가 한 벌**이다

**자기 점검**
- 코드 한 줄을 고쳤을 때 실제로 다시 전송되는 것은 무엇인가?
- 이미지에 들어 있는데 "파일이 아닌 것"은 무엇인가?

## 3.2 유니온 파일 시스템

**로우레벨의 불편함**: 층이 여러 개인데 컨테이너 안에서는 하나의 디렉터리로 보여야 한다.
층마다 디렉터리를 따로 뒤지면 느리고 복잡하다.

**해결**: **overlay2** 가 여러 디렉터리를 겹쳐 하나처럼 보여준다.
같은 경로가 여러 층에 있으면 **위층이 이긴다.**

- 아래층 파일은 사라지지 않고 **가려질 뿐**이다 (whiteout)
- 그래서 **이미지에서 파일을 지워도 용량이 줄지 않는다**

**자기 점검**
- `RUN rm big.tar.gz` 를 했는데 이미지 크기가 그대로인 이유는?
- 받고 풀고 지우는 것을 한 `RUN` 에 묶으면 왜 용량이 줄어드는가?

## 3.3 이미지 내부 구조 — manifest · config · digest

**로우레벨의 불편함**: "이미지"를 파일 하나로 생각하면
같은 태그가 CPU 아키텍처마다 다른 것을 설명할 수 없다.

**해결**: 이미지는 **JSON 두 개와 레이어 묶음**이다.

| 구성 | 담는 것 |
|---|---|
| manifest | 이 이미지가 쓰는 config 와 레이어들의 digest 목록 |
| config | 실행 명령, 환경변수, 작업 디렉터리, 빌드 히스토리 |
| layer | 실제 파일들. tar 로 압축돼 있다 |
| manifest list | 아키텍처별 manifest 를 묶은 것 (multi-arch) |

모든 조각이 **내용의 해시(digest)로 식별**된다. 내용이 같으면 digest 가 같고,
그래서 **이미 받은 층은 다시 안 받는다.**

- `docker pull` 이 "Already exists" 를 찍는 것이 이 때문이다
- 태그는 manifest 를 가리키는 **이름표**일 뿐이다

**자기 점검**
- 같은 `mysql:8` 태그가 ARM 맥과 x86 서버에서 다른 파일인데도 동작하는 이유는?
- 콘텐츠 주소 방식(digest)이 전송량을 줄이는 원리는?

## 3.4 빌드 캐시

**로우레벨의 불편함**: 매번 처음부터 빌드하면 의존성 설치에만 몇 분이 든다.

**해결**: 같은 명령은 **이전 층을 재사용**한다. 단, **한 층이 바뀌면 그 아래 전부**가 다시 만들어진다.

| 명령 | 캐시 키 |
|---|---|
| `RUN` | **명령 문자열 그 자체** |
| `COPY`, `ADD` | 복사되는 파일들의 체크섬 |
| `FROM` | 베이스 이미지의 다이제스트 |

- 자주 바뀌는 것을 **아래에** 둔다. `COPY package.json` → `RUN install` → `COPY . .`
- `RUN` 이 문자열만 본다는 점이 함정이다. `apt-get update` 와 `install` 을 `&&` 로 묶어야 한다

**자기 점검**
- 소스를 먼저 복사하면 왜 매번 의존성을 다시 설치하게 되는가?
- 몇 달 뒤 빌드했는데 옛날 패키지가 설치되는 이유는?

## 3.5 용량 줄이기와 멀티 스테이지

**로우레벨의 불편함**: 컴파일러·빌드 캐시·소스가 최종 이미지에 그대로 남는다.
운영에 필요 없는 것이 수백 MB 를 차지하고, **공격 표면도 넓어진다.**

**해결**: **멀티 스테이지 빌드**로 빌드 단계와 실행 단계를 나눈다.
`COPY --from=build` 로 결과물만 가져오면 앞 단계는 통째로 버려진다.

베이스 선택도 크게 작용한다.

| 베이스 | 성격 |
|---|---|
| `ubuntu`, `debian` | 가장 익숙하고 도구가 다 있다. 크다 |
| `-slim` | 문서·로케일 등을 뺀 것 |
| `-alpine` | musl libc 기반. 아주 작지만 glibc 전제 바이너리가 깨질 수 있다 |
| `distroless` | 셸도 패키지 관리자도 없다. 가장 안전하고 디버깅이 어렵다 |

- `.dockerignore` 를 빠뜨리면 로컬 `node_modules` 와 `.git` 이 빌드 컨텍스트에 통째로 들어간다

**자기 점검**
- 멀티 스테이지에서 앞 단계의 파일이 최종 이미지에 안 남는 이유는?
- alpine 으로 바꿨더니 바이너리가 안 도는 경우가 생기는 이유는?

## 3.6 태그와 다이제스트

**로우레벨의 불편함**: `mysql:8` 은 **움직이는 이름표**다. 패치가 나오면 가리키는 실체가 바뀐다.
"어제는 됐는데 오늘 안 된다"의 상당수가 여기서 온다.

**해결**: 불변 식별자인 **다이제스트**(`@sha256:...`)로 고정한다.

- `latest` 는 "최신"이 아니라 **태그를 안 줬을 때의 기본 이름**일 뿐이다
- 운영 배포는 다이제스트, 개발은 태그 정도가 현실적인 타협이다

**자기 점검**
- `latest` 가 최신을 보장하지 않는 이유는?
- 태그와 다이제스트를 각각 어디에 쓰는 것이 맞는가?

## 3.7 이미지를 뜯어보기

**로우레벨의 불편함**: 이미지가 왜 큰지, 어느 층이 범인인지 눈으로 볼 방법이 없으면
용량 최적화가 추측이 된다.

**해결**: 층별로 들여다보는 수단이 있다.

```bash
docker history 이미지      # 층마다 명령과 크기
docker image inspect 이미지 # config 전체
docker save 이미지 | tar tv # 안에 든 파일 목록
dive 이미지                 # 층을 오가며 파일 변화를 본다 (외부 도구)
```

- `docker history` 에서 유독 큰 층을 먼저 본다. 대개 패키지 설치나 `COPY . .` 다
- 빌드 인자로 넘긴 값이 히스토리에 그대로 남는 것도 여기서 확인된다

**자기 점검**
- 이미지가 갑자기 커졌을 때 가장 먼저 치는 명령은?
- `docker history` 로 비밀이 샐 수 있는 경로는?

# 📚 PART 4 — 컨테이너 실행과 격리

> **목표**: 격리가 커널의 어떤 기능으로 만들어지는지 알고, PID 1 함정을 피한다.

## 4.1 이미지와 컨테이너의 관계

**로우레벨의 불편함**: 이미지는 읽기 전용인데 프로그램은 파일을 쓴다.

**해결**: 이미지 층들 **위에 쓰기 가능한 층 하나**를 얹어 컨테이너로 만든다.
이미지는 끝까지 안 변한다. 같은 이미지로 컨테이너를 열 개 띄우면 **쓰기 층만 열 개**다.

- 이미지 : 컨테이너 = 클래스 : 인스턴스
- 컨테이너를 지우면 쓰기 층도 사라진다. 이미지는 남는다

**자기 점검**
- 같은 이미지로 띄운 컨테이너 둘이 서로의 변경을 못 보는 이유는?
- 컨테이너를 지웠는데 디스크가 안 줄었다면 무엇을 봐야 하는가?

## 4.2 컨테이너의 생명주기

**로우레벨의 불편함**: `run`, `start`, `exec`, `stop`, `rm` 의 차이를 모르면
"분명히 멈췄는데 목록에 남아 있다", "같은 이름을 못 쓴다" 같은 상황에서 막힌다.

**해결**: 상태가 몇 개뿐이다.

```
created ──start──► running ──stop──► exited ──rm──► (없음)
                      │  ▲
                   pause│ │unpause
                      ▼  │
                    paused
```

| 명령 | 하는 일 |
|---|---|
| `run` | 이미지로 컨테이너를 만들고 바로 시작 (`create` + `start`) |
| `exec` | **이미 도는** 컨테이너 안에서 명령을 더 실행 |
| `stop` | `SIGTERM` 후 유예 시간, 안 죽으면 `SIGKILL` |
| `kill` | 바로 `SIGKILL` |
| `rm` | 멈춘 컨테이너와 쓰기 층을 지운다 |

- `docker ps` 는 도는 것만, `docker ps -a` 는 멈춘 것까지 보여준다
- 이름 충돌은 대개 **멈춘 채 남아 있는 컨테이너** 때문이다. `--rm` 을 붙이면 종료 시 자동 삭제된다

**자기 점검**
- `exec` 로 띄운 프로세스는 메인 프로세스가 죽으면 어떻게 되는가?
- `stop` 과 `kill` 중 데이터 손상 위험이 큰 쪽은?

## 4.3 namespace — 보이는 것을 나눈다

**로우레벨의 불편함**: 한 호스트의 프로세스들은 서로의 PID·네트워크·마운트를 전부 본다.
`chroot` 는 파일 시스템만 바꿀 뿐 나머지는 그대로다.

**해결**: 리눅스 **namespace** 로 영역별로 시야를 분리한다.

| namespace | 나누는 것 |
|---|---|
| `pid` | 프로세스 목록. 컨테이너 안에서는 자기 프로세스가 PID 1 |
| `mnt` | 마운트된 파일 시스템 |
| `net` | 네트워크 인터페이스, 포트, 라우팅 |
| `uts` | 호스트명 |
| `ipc` | 공유 메모리, 세마포어 |
| `user` | UID·GID 매핑 |

namespace 는 **공유할 수도 있다.** `--network container:대상` 으로 다른 컨테이너의
네트워크를 그대로 쓰면 둘이 `localhost` 로 통신한다. 쿠버네티스의 Pod 가 이 방식이다.

**자기 점검**
- `chroot` 로는 부족한 이유를 namespace 종류와 연결해 설명하면?
- Pod 안의 컨테이너들이 `localhost` 로 통신할 수 있는 이유는?

## 4.4 cgroup — 쓸 수 있는 양을 나눈다

**로우레벨의 불편함**: 격리해도 **자원은 공유**한다. 컨테이너 하나가 메모리를 다 먹으면
호스트 전체가 멈춘다.

**해결**: **cgroup** 으로 CPU·메모리·IO 한도를 건다. 한도를 넘기면 커널의 OOM killer 가 그 프로세스를 죽인다.

- 컨테이너가 이유 없이 사라졌다면 `docker inspect --format '{{.State.OOMKilled}}'` 를 먼저 본다
- JVM 은 Java 10 부터 cgroup 한도를 인식한다. 그 전 버전은 `-Xmx` 를 직접 줘야 했다
- `--cpus 1.5` 는 코어를 고정하는 것이 아니라 **CPU 시간의 비율**을 제한한다

**자기 점검**
- namespace 만 있고 cgroup 이 없다면 어떤 사고가 나는가?
- 애플리케이션이 호스트 전체 메모리를 기준으로 동작하면 왜 위험한가?

## 4.5 PID 1 과 시그널

**로우레벨의 불편함**: 리눅스에서 PID 1 은 특별 취급을 받는다.
**기본 시그널 핸들러가 없어서** `SIGTERM` 을 직접 처리하지 않으면 무시된다.
그래서 `docker stop` 이 유예 시간을 기다렸다가 `SIGKILL` 로 강제 종료하는 일이 흔하다.

**해결**: 애플리케이션이 PID 1 이 되게 하고, 그 안에서 `SIGTERM` 을 처리한다.

- `CMD npm start` 는 셸이 PID 1 이 되어 시그널이 자식에게 안 간다
- `CMD ["npm", "start"]` (exec form) 을 쓴다
- PID 1 은 고아 프로세스를 거둘 책임도 진다. 자식을 많이 만드는 앱이면 `tini` 같은 init 을 넣는다

**자기 점검**
- 종료가 항상 유예 시간만큼 걸린다면 무엇을 의심해야 하는가?
- shell form 과 exec form 의 차이가 시그널 전달에 왜 영향을 주는가?

# 📚 PART 5 — 데이터와 볼륨

> **목표**: 컨테이너가 사라져도 남아야 하는 데이터를 어디에 두는지 판단한다.

## 5.1 쓰기 층과 copy-on-write

**로우레벨의 불편함**: 컨테이너 안에서 이미지에 있던 파일을 고치면
**파일 전체를 쓰기 층으로 복사한 뒤** 고친다. 1GB 파일의 한 바이트만 바꿔도 1GB 가 복사된다.

**해결**: 계속 쓰이는 데이터는 **쓰기 층 밖**에 둔다. 볼륨은 CoW 를 거치지 않는다.

**자기 점검**
- DB 데이터를 컨테이너 쓰기 층에 두면 왜 느려지는가?
- CoW 가 이미지 공유에는 유리한데 쓰기에는 불리한 이유는?

## 5.2 volume · bind mount · tmpfs

**로우레벨의 불편함**: 컨테이너를 지우면 쓰기 층도 같이 사라진다.
호스트 경로를 직접 붙이면 보존은 되지만 **경로가 환경마다 다르다.**

**해결**: 용도별로 세 가지를 나눠 쓴다.

| 방식 | 쓰는 곳 | 성격 |
|---|---|---|
| volume | DB 데이터 | Docker 가 관리. 호스트 경로를 몰라도 된다 |
| bind mount | 개발 중 소스, 설정 파일 | 호스트의 특정 경로를 그대로 연결 |
| tmpfs | 비밀값, 임시 파일 | 메모리에만. 컨테이너가 죽으면 사라진다 |

- `docker compose down` 은 컨테이너만 지운다. **`-v` 를 붙이면 볼륨까지 지운다**
- 초기화 스크립트(`/docker-entrypoint-initdb.d`)는 **데이터 디렉터리가 비어 있을 때만** 실행된다
- 빈 디렉터리를 bind mount 하면 이미지에 있던 파일이 **가려진다.** `node_modules` 가 사라진 것처럼 보이는 원인

**자기 점검**
- 같은 설정으로 다시 띄웠는데 초기화 SQL 이 안 도는 이유는?
- 소스를 bind mount 했더니 `node_modules` 가 없어졌다면 무슨 일이 일어난 것인가?

## 5.3 스토리지 드라이버

**로우레벨의 불편함**: 유니온 파일 시스템 구현이 하나가 아니다.
드라이버에 따라 성능과 제약이 다른데, 모르면 "왜 느리지"에서 멈춘다.

**해결**: 지금은 사실상 `overlay2` 하나다. 나머지는 특수한 경우다.

| 드라이버 | 성격 |
|---|---|
| `overlay2` | 기본값. 거의 모든 환경 |
| `fuse-overlayfs` | rootless 환경. 조금 느리다 |
| `btrfs`, `zfs` | 그 파일 시스템을 쓰는 호스트 |
| `vfs` | CoW 없이 전부 복사. 테스트용. 매우 느리고 디스크를 많이 먹는다 |

- `docker info` 로 현재 드라이버를 확인한다
- 층이 아주 많으면(수십 개) overlay2 도 조회가 느려진다. 층을 줄이는 또 하나의 이유

**자기 점검**
- `vfs` 로 떨어졌다면 무엇을 확인해야 하는가?
- 층 개수가 성능에 영향을 주는 이유는?

## 5.4 백업과 이전

**로우레벨의 불편함**: 볼륨은 호스트 어딘가에 있지만 경로를 직접 다루기 번거롭고,
도커 버전·드라이버에 따라 위치가 다르다.

**해결**: 임시 컨테이너를 띄워 볼륨을 마운트하고 `tar` 로 말아 내보낸다.
DB 는 파일 복사보다 `mysqldump` 같은 **논리 백업**이 안전하다.

```bash
docker run --rm -v mysql-data:/data -v "$PWD":/backup alpine \
  tar czf /backup/mysql-data.tar.gz -C /data .
```

**자기 점검**
- 실행 중인 DB 의 데이터 디렉터리를 그냥 복사하면 왜 위험한가?
- 볼륨 이름 앞에 프로젝트 이름이 붙는 것이 백업 복원에 왜 중요한가?

# 📚 PART 6 — 네트워크

> **목표**: 컨테이너끼리, 호스트와, 바깥과 어떻게 통신하는지 구분한다.

## 6.1 기본 bridge 와 포트 매핑

**로우레벨의 불편함**: 컨테이너는 자기만의 네트워크 namespace 를 가져서
밖에서 바로 닿을 수 없다.

**해결**: `-p 3307:3306` 으로 **호스트 포트를 컨테이너 포트에 연결**한다.
왼쪽이 호스트, 오른쪽이 컨테이너다.

- 순서를 뒤집으면 엉뚱한 포트가 열린다
- `-p 127.0.0.1:3307:3306` 처럼 **주소를 붙이면 외부에서 못 들어온다.** 개발 DB 는 이렇게 묶는 게 안전하다
- 호스트에 이미 그 포트를 쓰는 프로세스가 있으면 기동이 실패한다

**자기 점검**
- 컨테이너끼리 통신할 때도 공개 포트를 써야 하는가?
- 개발용 DB 를 `-p 3307:3306` 으로 열면 무엇이 위험한가?

## 6.2 사용자 정의 네트워크와 DNS

**로우레벨의 불편함**: 기본 bridge 에서는 컨테이너 IP 가 재시작마다 바뀐다.
IP 를 설정에 박으면 깨진다. 예전에는 `--link` 로 묶었지만 폐기됐다.

**해결**: 사용자 정의 네트워크를 만들면 **컨테이너 이름이 그대로 호스트명**이 된다.
Compose 는 이걸 자동으로 해준다.

```
app 컨테이너 ──► db:3306        (같은 네트워크, 서비스 이름으로)
브라우저    ──► localhost:3307  (호스트에서, 공개된 포트로)
```

- 네트워크를 여러 개 두고 서비스를 나눠 붙이면 **닿을 수 있는 범위를 제한**할 수 있다
- DB 를 프론트엔드 네트워크에서 빼두면 웹이 뚫려도 DB 로 못 간다

**자기 점검**
- 앱을 컨테이너 밖에서 돌릴 때 `db:3306` 으로 못 붙는 이유는?
- 네트워크를 분리하면 보안상 무엇이 좋아지는가?

## 6.3 호스트와 컨테이너 사이

**로우레벨의 불편함**: 컨테이너 안에서 **호스트에서 도는 서비스**에 붙어야 할 때가 있다.
개발 중 앱은 호스트에, DB 는 컨테이너에 두는 경우가 그렇다. `localhost` 는 컨테이너 자신을 가리킨다.

**해결**: 호스트를 가리키는 이름을 쓴다.

- Docker Desktop(Windows·macOS): `host.docker.internal` 이 기본 제공된다
- 리눅스: `--add-host=host.docker.internal:host-gateway` 를 줘야 한다

반대로 **호스트에서 컨테이너로** 갈 때는 공개 포트를 쓴다. 이 비대칭을 헷갈리면
"분명 같은 PC 인데 왜 안 되지"에서 막힌다.

**자기 점검**
- 컨테이너 안의 `localhost` 는 무엇을 가리키는가?
- 앱은 호스트, DB 는 컨테이너일 때 접속 주소를 각각 어떻게 적는가?

## 6.4 host · none · overlay

**로우레벨의 불편함**: bridge 는 NAT 를 거쳐 약간의 오버헤드가 있고,
여러 호스트에 걸친 통신은 아예 안 된다.

**해결**: 용도에 따라 드라이버를 바꾼다.

| 드라이버 | 쓰는 곳 |
|---|---|
| `bridge` | 기본. 단일 호스트 |
| `host` | 네트워크 성능이 중요할 때. 격리를 포기한다 |
| `none` | 네트워크가 필요 없는 배치 작업 |
| `overlay` | 여러 호스트에 걸친 통신 (Swarm·K8s) |

**자기 점검**
- `host` 네트워크를 쓰면 포트 매핑이 왜 의미 없어지는가?
- 단일 호스트에서 overlay 가 필요 없는 이유는?

# 📚 PART 7 — Dockerfile 과 BuildKit

> **목표**: 명령 하나하나가 층과 실행에 어떤 영향을 주는지 알고, 지금의 빌더를 제대로 쓴다.

## 7.1 명령어와 층

**로우레벨의 불편함**: 명령을 생각 없이 나열하면 층이 쓸데없이 늘고 캐시가 깨진다.

**해결**: 어떤 명령이 층을 만드는지 구분한다.

- 층을 만드는 것: `FROM`, `RUN`, `COPY`, `ADD`
- 메타데이터만 바꾸는 것: `CMD`, `ENTRYPOINT`, `ENV`, `EXPOSE`, `WORKDIR`, `USER`, `LABEL`
- `ADD` 는 URL 다운로드와 압축 해제까지 한다. 의도치 않은 동작이 많아 **`COPY` 를 기본으로** 쓴다
- `EXPOSE` 는 포트를 열지 않는다. **문서용 표시**일 뿐이다

**자기 점검**
- `EXPOSE` 를 적었는데 밖에서 못 붙는 이유는?
- `RUN` 을 `&&` 로 묶는 것이 캐시와 용량 양쪽에 영향을 주는 이유는?

## 7.2 CMD 와 ENTRYPOINT

**로우레벨의 불편함**: 둘 다 "실행할 것"을 정하는데 역할이 헷갈린다.

**해결**: `ENTRYPOINT` 는 **바꾸지 않을 실행 파일**, `CMD` 는 **기본 인자**다.
`docker run 이미지 인자` 로 주면 `CMD` 가 교체되고 `ENTRYPOINT` 는 남는다.

- shell form 은 `/bin/sh -c` 를 거쳐 **시그널이 안 간다**. exec form 을 쓴다
- `ENTRYPOINT` 에 스크립트를 두고 끝에 `exec "$@"` 를 쓰면 시그널이 유지된다

**자기 점검**
- `docker run` 뒤에 명령을 붙이면 무엇이 바뀌는가?
- 진입 스크립트 끝에 `exec` 를 쓰는 이유는?

## 7.3 빌드 컨텍스트와 .dockerignore

**로우레벨의 불편함**: `docker build .` 은 **그 디렉터리 전부**를 빌더에 먼저 전송한다.
`node_modules` 와 `.git` 이 있으면 수백 MB 가 매번 오간다.

**해결**: `.dockerignore` 로 전송 대상에서 뺀다. 빌드도 빨라지고 이미지에 비밀 파일이 섞여 들어가는 것도 막는다.

**자기 점검**
- 빌드가 컨텍스트 전송에서 오래 걸리면 무엇을 봐야 하는가?
- `.dockerignore` 가 보안에도 도움이 되는 이유는?

## 7.4 ARG 와 ENV

**로우레벨의 불편함**: 설정을 이미지에 하드코딩하면 환경마다 이미지를 따로 만들어야 한다.

**해결**: **`ARG` 는 빌드 시점**, **`ENV` 는 실행 시점**이다.

- `ARG` 는 최종 이미지에 안 남지만 **빌드 히스토리에는 남는다.** 비밀을 넣으면 안 된다
- `ENV` 로 넣은 값은 `docker inspect` 로 그대로 보인다. 비밀은 여기도 아니다
- 비밀을 다루는 제대로 된 방법은 7.6 과 PART 9 에서 본다

**자기 점검**
- `ARG` 로 받은 토큰이 최종 이미지에 없는데도 위험한 이유는?
- 같은 이미지를 개발·운영에 함께 쓰려면 설정을 어디서 주입해야 하는가?

## 7.5 HEALTHCHECK

**로우레벨의 불편함**: 프로세스가 떠 있다고 **서비스가 준비된 것은 아니다.**
DB 는 기동 후 수십 초가 지나야 접속을 받는다.

**해결**: `HEALTHCHECK` 로 실제 응답 가능 여부를 검사한다.

- `start_period` 동안의 실패는 재시도 횟수에 세지 않는다. 이게 없으면 "준비 중"을 "실패"로 센다
- 검사 명령은 **컨테이너 안에 있어야 한다.** slim 이미지에 `curl` 이 없어 늘 실패하는 경우가 흔하다

**자기 점검**
- `depends_on` 만으로 기동 순서 문제가 안 풀리는 이유는?
- `start_period` 가 없으면 DB 가 왜 unhealthy 로 찍히는가?

## 7.6 BuildKit — 캐시 마운트

**로우레벨의 불편함**: 의존성 캐시(`~/.m2`, `~/.npm`)를 층에 남기면 **이미지가 커지고**,
안 남기면 **매번 다시 받는다.** 둘 다 싫은 상황이 오래 이어졌다.

**해결**: BuildKit(Docker Engine 23부터 기본 빌더)의 **캐시 마운트**는
빌드 중에만 붙었다가 **층에는 안 남는** 디렉터리를 준다.

```dockerfile
RUN --mount=type=cache,target=/root/.m2 \
    mvn -B package
```

- 다음 빌드에서도 그 디렉터리가 유지된다. 이미지에는 안 들어간다
- `apt` 캐시, `npm` 캐시, Go 모듈 캐시에 똑같이 쓴다

BuildKit 은 그 외에도 **서로 의존하지 않는 단계를 병렬로** 돌리고,
최종 이미지에 안 쓰이는 단계는 **아예 실행하지 않는다.**

**자기 점검**
- 캐시 마운트가 레이어 캐시와 다른 점은?
- 멀티 스테이지에서 안 쓰이는 단계를 건너뛸 수 있는 이유는?

## 7.7 BuildKit — 시크릿 마운트

**로우레벨의 불편함**: 사설 저장소에서 패키지를 받으려면 빌드 중에 토큰이 필요하다.
`ARG` 로 주면 히스토리에 남고, 파일로 `COPY` 하면 층에 남는다. 지워도 아래 층에 남는다.

**해결**: **시크릿 마운트**는 빌드 중에만 파일로 존재하고 **어느 층에도 안 남는다.**

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci
```

```bash
docker build --secret id=npmrc,src=$HOME/.npmrc .
```

- SSH 가 필요하면 `--mount=type=ssh` 로 에이전트를 빌려준다
- 이걸 알고 나면 "빌드 중 비밀"은 더 이상 어려운 문제가 아니다

**자기 점검**
- `ARG` · `COPY` · 시크릿 마운트가 각각 어디에 흔적을 남기는가?
- 빌드 후 `rm` 으로 지우는 것이 왜 소용없는가?

## 7.8 멀티 아키텍처 빌드

**로우레벨의 불편함**: Apple Silicon 에서 만든 이미지가 x86 서버에서 안 돈다.
`exec format error` 가 뜬다.

**해결**: `buildx` 로 **여러 아키텍처를 한 번에** 빌드하고 manifest list 로 묶는다.

```bash
docker buildx build --platform linux/amd64,linux/arm64 -t myapp:1.0 --push .
```

- 받는 쪽은 자기 아키텍처에 맞는 것을 **알아서 고른다**
- 네이티브가 아닌 아키텍처는 에뮬레이션(QEMU)으로 빌드돼 느리다. CI 에서는 아키텍처별 러너를 쓰는 편이 빠르다

**자기 점검**
- 같은 태그가 기기마다 다른 바이너리를 주는 구조를 3.3 과 연결해 설명하면?
- 로컬 맥에서 빌드한 이미지를 서버에 올리기 전에 확인할 것은?

# 📚 PART 8 — Compose 와 개발 워크플로

> **목표**: 여러 컨테이너를 재현 가능하게 묶고, 개발 환경을 어디까지 컨테이너에 넣을지 정한다.

## 8.1 서비스·네트워크·볼륨

**로우레벨의 불편함**: 컨테이너가 둘 이상이면 `docker run` 을 여러 번 치고
포트·볼륨·환경변수·네트워크를 매번 손으로 맞춰야 한다. 그 명령은 **내 셸 히스토리에만** 있다.

**해결**: Compose 파일 하나에 적고 `docker compose up -d` 로 띄운다.
파일이 레포에 들어가므로 "내 PC에서만 되는" 설정이 사라진다.

- 네트워크를 안 적어도 **기본 네트워크를 자동으로 만들고** 서비스 이름을 호스트명으로 쓴다

**자기 점검**
- Compose 가 `docker run` 반복과 비교해 주는 진짜 이득은 무엇인가?
- 네트워크를 안 적었는데 서비스 이름으로 통신되는 이유는?

## 8.2 프로젝트 이름이 모든 자원에 붙는다

**로우레벨의 불편함**: 폴더 이름을 바꿨더니 DB 데이터가 사라진 것처럼 보인다.

**해결**: Compose 는 **프로젝트 이름**(기본값은 폴더 이름)으로 컨테이너·네트워크·볼륨 이름을 짓는다.
이름이 바뀌면 다른 프로젝트가 되고, 옛 볼륨은 그대로 남아 있다.

- 파일에 `name:` 을 적어 고정하면 폴더를 옮겨도 안전하다

**자기 점검**
- 폴더 이름을 바꿨을 때 실제로 사라진 것은 무엇이고 남아 있는 것은 무엇인가?
- 같은 compose 파일로 두 벌을 동시에 띄우려면 무엇을 바꿔야 하는가?

## 8.3 파일 병합과 profiles

**로우레벨의 불편함**: 개발·운영 설정을 파일로 복사해 두 벌 유지하면 금세 어긋난다.

**해결**: 공통 파일 + override 파일로 나눠 **합쳐서** 쓴다.
가끔만 필요한 서비스는 `profiles` 로 묶어 평소엔 안 뜨게 한다.

| 타입 | 합쳐지는 방식 |
|---|---|
| 단일 값(`image`, `restart`) | 나중 파일이 **덮어쓴다** |
| 목록(`ports`, `volumes`) | **이어붙인다** |
| 맵(`environment`) | 키 단위로 병합 |
| `command`, `entrypoint` | 통째로 교체 |

- 목록이 이어붙는다는 점이 함정이다. 포트를 "바꾸려" 했는데 **둘 다 열린다**
- `docker compose config` 로 합쳐진 최종 설정을 확인한다

**자기 점검**
- override 에서 포트를 바꾸려 했는데 둘 다 열렸다면 무엇을 고쳐야 하는가?
- `-f` 를 직접 쓰면 override 자동 병합이 꺼지는 이유는?

## 8.4 환경변수 치환

**로우레벨의 불편함**: `.env` 와 `environment:` 를 같은 것으로 착각하면
값이 왜 안 들어가는지 알 수 없다.

**해결**: 둘은 **완전히 다른 통로**다.

```
.env 파일     → compose 파일 안의 ${...} 치환   (Compose 가 읽음)
environment:  → 컨테이너 안의 환경변수          (컨테이너가 받음)
env_file:     → 컨테이너 안의 환경변수를 파일에서
```

- `${VAR:-기본값}`, `${VAR:?에러메시지}` 를 쓸 수 있다. 후자는 값이 없으면 기동을 거부한다

**자기 점검**
- `.env` 에 적은 값이 컨테이너 안에서 안 보이는 이유는?
- 비밀번호가 빠졌을 때 조용히 뜨는 대신 실패하게 하려면?

## 8.5 기동 순서 — healthcheck 로도 안 되는 것

**로우레벨의 불편함**: `depends_on` 은 **기동 순서만** 정한다.
`condition: service_healthy` 를 붙이면 준비까지 기다리지만, 그래도 부족하다.
**운영 중에 DB 가 재시작하면** 앱은 이미 떠 있는 상태에서 연결이 끊긴다.

**해결**: 기동 순서는 보조 수단이고, **애플리케이션의 재시도가 진짜 해법**이다.

```
depends_on + healthcheck  →  첫 기동을 매끄럽게
커넥션 풀 재연결·재시도    →  운영 중 끊김까지 버팀
```

- `wait-for-it.sh` 같은 스크립트도 첫 기동만 해결한다
- 커넥션 풀은 대개 재연결을 지원한다. 그 설정을 켜는 것이 먼저다

**자기 점검**
- `service_healthy` 로도 못 막는 상황은 무엇인가?
- "기동 순서 문제"를 애플리케이션 쪽에서 푸는 것이 왜 더 견고한가?

## 8.6 개발 환경 — 어디까지 컨테이너에 넣을까

**로우레벨의 불편함**: 전부 호스트에 설치하면 환경이 더러워지고,
전부 컨테이너에 넣으면 **핫리로드가 느려지고 디버거 붙이기가 번거롭다.**

**해결**: **의존 서비스만 컨테이너, 앱은 호스트**가 현실적인 타협이다.

| 대상 | 어디에 | 이유 |
|---|---|---|
| DB·캐시·메시지 큐 | 컨테이너 | 설치가 번거롭고 버전이 갈린다 |
| 개발 중인 앱 | 호스트 | 핫리로드와 디버거가 빠르다 |

- 앱이 컨테이너 밖이면 DB 주소가 `db:3306` 이 아니라 `localhost:3307` 이 된다(6.3)
- 팀 전체 환경을 고정하고 싶으면 **Dev Containers** 로 개발 환경 자체를 이미지화한다
- bind mount 로 소스를 넣는 방식은 Windows·macOS 에서 느릴 수 있다(PART 12)

**자기 점검**
- 앱까지 컨테이너에 넣었을 때 생기는 불편을 셋 들면?
- 운영은 전부 컨테이너인데 개발만 다르게 가도 되는 이유는?

# 📚 PART 9 — 보안

> **목표**: 기본값이 안전하지 않은 지점을 알고, 권한을 최소로 줄인다.

## 9.1 도커 소켓을 마운트하면 무슨 일이 일어나는가

**로우레벨의 불편함**: 컨테이너 안에서 다른 컨테이너를 제어하려고
`/var/run/docker.sock` 을 마운트하는 예제가 흔하다. CI 러너, 모니터링 도구에서 자주 본다.

**해결**: 이게 무슨 뜻인지부터 알아야 한다. **그 소켓은 데몬 전체의 제어권**이다.

```bash
# 소켓이 있으면 이 한 줄로 호스트 루트를 잡는다
docker run -v /:/host -it alpine chroot /host sh
```

컨테이너 안에서 이 명령을 치면 호스트 파일 시스템 전체를 루트로 쓴다.
**격리가 의미를 잃는다.**

- 꼭 필요하면 **소켓 프록시**를 두고 허용할 API 만 연다
- 또는 데몬이 필요 없는 도구(buildah, kaniko)를 쓴다
- "DinD(Docker in Docker)"는 `--privileged` 를 요구한다. 더 위험하다

**자기 점검**
- 소켓 마운트가 `--privileged` 와 사실상 같은 위험인 이유는?
- CI 에서 이미지를 빌드해야 할 때 소켓을 안 쓰는 방법은?

## 9.2 루트로 돌리지 않기

**로우레벨의 불편함**: 컨테이너 안의 루트는 기본적으로 **호스트의 UID 0** 과 같다.
bind mount 한 디렉터리에 쓰면 호스트에 루트 소유 파일이 생기고,
컨테이너 탈출 취약점이 터지면 그대로 호스트 권한이 된다.

**해결**: 이미지에서 전용 사용자를 만들고 `USER` 로 전환한다.

```dockerfile
RUN addgroup -S app && adduser -S app -G app
USER app
```

- 1024 미만 포트를 열려면 루트가 필요했지만, `NET_BIND_SERVICE` capability 만 주면 된다
- **user namespace**(`--userns-remap`)를 켜면 컨테이너의 루트가 호스트의 비권한 UID 로 매핑된다
- rootless 모드는 데몬 자체를 사용자 권한으로 돌린다

**자기 점검**
- 컨테이너 루트와 호스트 루트가 같은 UID 라는 사실이 왜 문제인가?
- `USER` 를 썼는데도 user namespace 가 따로 필요한 이유는?

## 9.3 capability 줄이기

**로우레벨의 불편함**: 리눅스의 루트 권한은 **하나가 아니라 수십 개의 capability 묶음**이다.
Docker 는 기본적으로 위험한 것 상당수를 빼지만, 남은 것도 앱에는 대부분 불필요하다.

**해결**: 전부 버리고 필요한 것만 되돌린다.

```bash
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE myapp
```

| capability | 하는 일 |
|---|---|
| `NET_BIND_SERVICE` | 1024 미만 포트 바인딩 |
| `CHOWN` | 파일 소유자 변경 |
| `SYS_ADMIN` | 거의 루트. 주면 안 된다 |
| `NET_RAW` | raw 소켓. ping 에 쓰이지만 공격에도 쓰인다 |

- 대부분의 웹 애플리케이션은 `--cap-drop=ALL` 로도 잘 돈다. 안 되면 하나씩 되돌리며 찾는다

**자기 점검**
- "루트 권한"을 쪼갠다는 발상이 왜 보안에 유리한가?
- `--privileged` 가 위험한 이유를 capability 로 설명하면?

## 9.4 읽기 전용 루트 파일 시스템

**로우레벨의 불편함**: 침입자가 컨테이너 안에 도구를 내려받아 설치할 수 있으면
그다음 단계로 넘어가기 쉬워진다.

**해결**: 루트 파일 시스템을 읽기 전용으로 만들고, 써야 하는 경로만 tmpfs 로 연다.

```bash
docker run --read-only --tmpfs /tmp myapp
```

- 애플리케이션이 어디에 쓰는지 모르면 일단 켜보고 실패하는 경로를 열어주면 된다
- 로그를 stdout 으로 내는 습관(11.1)이 여기서도 도움이 된다

**자기 점검**
- 읽기 전용으로 만들면 공격자가 구체적으로 무엇을 못 하게 되는가?
- 애플리케이션이 쓰기를 필요로 하는 경로를 어떻게 찾는가?

## 9.5 seccomp 와 AppArmor

**로우레벨의 불편함**: 컨테이너 안 프로세스도 **커널에 시스템 콜을 직접 날린다.**
커널 취약점은 대개 특정 시스템 콜을 통해 터진다.

**해결**: 쓸 수 있는 시스템 콜 자체를 줄인다.

- **seccomp**: Docker 는 기본 프로파일로 위험한 시스템 콜을 막는다. `--security-opt seccomp=unconfined` 는 그걸 끄는 것이라 쓰지 않는다
- **AppArmor / SELinux**: 파일·네트워크 접근을 정책으로 제한한다
- `--security-opt no-new-privileges` 는 setuid 로 권한이 올라가는 것을 막는다

**자기 점검**
- 예제에서 `seccomp=unconfined` 를 보면 왜 의심해야 하는가?
- capability 와 seccomp 가 막는 대상은 어떻게 다른가?

## 9.6 시크릿을 다루는 법

**로우레벨의 불편함**: 비밀을 넣을 자리마다 함정이 있다.

| 방법 | 어디에 남는가 |
|---|---|
| 이미지에 파일로 | 층에 영구히. 지워도 아래 층에 |
| `ARG` | 빌드 히스토리 |
| `ENV` | `docker inspect`, 자식 프로세스 환경 |
| 명령행 인자 | 호스트의 프로세스 목록 |

**해결**: 용도별로 나눈다.

- 빌드 중: BuildKit 시크릿 마운트(7.7)
- 실행 중: Compose `secrets` 로 파일 마운트, 또는 외부 시크릿 관리자
- 그래도 환경변수를 쓸 거면, 최소한 **로그에 환경 전체를 찍지 않는지** 확인한다

**자기 점검**
- 환경변수가 "그럭저럭 쓰이지만 권장되지 않는" 이유는?
- 파일 마운트가 환경변수보다 나은 점은?

## 9.7 이미지 신뢰 — 서명과 스캔

**로우레벨의 불편함**: 받은 이미지 안에 뭐가 들었는지 모른다.
공식처럼 보이는 이름이 실제로는 남이 올린 것일 수 있다.

**해결**: 출처를 확인하고 내용을 검사한다.

- **서명**: cosign 으로 서명하고 배포 시 검증한다
- **스캔**: Trivy, Docker Scout 등으로 알려진 취약점을 본다. CI 에 붙여 자동화한다
- **SBOM**: 이미지에 든 패키지 목록을 산출물로 남긴다. 나중에 "그 취약점이 우리에게 있나"를 바로 답할 수 있다

베이스를 최신으로 유지하고 작게 쓰는 것(3.5)만으로도 알려진 취약점 상당수가 사라진다.

**자기 점검**

# 📚 PART 10 — 레지스트리와 배포

> **목표**: 만든 이미지를 남에게 안전하게 전달한다.

## 10.1 레지스트리 push/pull

**로우레벨의 불편함**: 이미지를 `docker save` 로 tar 를 만들어 주고받으면
버전 관리가 안 되고 용량도 크다.

**해결**: **레지스트리**에 올리고 받는다. 층 단위로 전송되므로 바뀐 것만 오간다.

- 이미지 이름은 `레지스트리/저장소:태그` 구조다. 생략하면 Docker Hub 다
- Docker Hub 는 익명 pull 에 **속도 제한**이 있다. CI 에서 자주 막힌다. 로그인하거나 미러를 쓴다

**자기 점검**

## 10.2 사설 레지스트리

**로우레벨의 불편함**: 사내 이미지를 공개 레지스트리에 올릴 수 없고,
외부 의존이 끊기면 배포가 멈춘다.

**해결**: 사설 레지스트리를 둔다.

- `registry:2` 이미지로 간단히 띄울 수 있다. 실제로는 Harbor, ECR, GCR 등을 쓴다
- 공개 이미지를 **미러링**해두면 외부 장애와 속도 제한에서 자유로워진다
- 사설 레지스트리가 HTTP 면 `insecure-registries` 설정이 필요하다. 사내망에서만 쓴다

**자기 점검**
- 공개 이미지를 미러링하는 것이 왜 안정성에 기여하는가?
- 레지스트리가 멈추면 이미 떠 있는 컨테이너는 어떻게 되는가?

## 10.3 CI 에서 빌드하기

**로우레벨의 불편함**: 개발자 PC 에서 빌드해 올리면 사람마다 결과가 다르고 추적이 안 된다.

**해결**: CI 에서 빌드·태깅·푸시를 자동화한다. 커밋 해시를 태그로 쓰면 **어느 코드가 떠 있는지** 역추적된다.

- CI 는 캐시가 없어 매번 처음부터 빌드한다. 레지스트리 캐시(`--cache-from`)를 쓴다
- 태그 전략: `1.2.3`(릴리스), `sha-abc1234`(추적), `main`(최신) 을 함께 단다

**자기 점검**
- 태그에 커밋 해시를 쓰는 것이 운영에서 왜 중요한가?
- CI 빌드가 로컬보다 느린 이유와 해결책은?

# 📚 PART 11 — 운영 · 디버깅 · 정리

> **목표**: 떠 있는 컨테이너에서 문제를 찾아내고, 디스크를 관리한다.

## 11.1 로그와 드라이버

**로우레벨의 불편함**: 컨테이너 안 파일에 로그를 쓰면 컨테이너가 사라질 때 같이 사라지고,
쓰기 층이 계속 커진다.

**해결**: **stdout/stderr 로 낸다.** 도커가 받아 로그 드라이버로 넘기고, 수집기가 가져간다.

| 드라이버 | 성격 |
|---|---|
| `json-file` | 기본값. `docker logs` 로 볼 수 있다. 용량이 계속 는다 |
| `local` | 더 효율적인 포맷. 회전이 기본으로 켜져 있다 |
| `journald` | systemd 로 보낸다 |
| `fluentd`, `gelf`, `awslogs` | 수집기로 바로 보낸다. `docker logs` 는 못 쓴다 |

- `json-file` 은 `max-size`, `max-file` 로 회전시키지 않으면 **무한히 쌓인다**
- 디스크가 꽉 찼을 때 범인이 로그인 경우가 흔하다

**자기 점검**
- 애플리케이션이 파일에 로그를 쓰도록 되어 있다면 컨테이너에서는 어떻게 바꾸는가?
- 수집기로 바로 보내는 드라이버를 쓰면 무엇을 잃는가?

## 11.2 리소스와 OOM

**로우레벨의 불편함**: 컨테이너가 조용히 사라지는데 로그에는 아무 흔적이 없다.

**해결**: 한도를 걸고(`-m`, `--cpus`), 죽었을 때 OOM 여부를 확인한다.

```bash
docker inspect --format '{{.State.OOMKilled}} {{.State.ExitCode}}' 이름
docker stats
```

- 종료 코드 137 은 `SIGKILL`(128+9), 143 은 `SIGTERM`(128+15) 이다
- OOM 이면 애플리케이션 한도(JVM 힙 등)가 컨테이너 한도보다 작은지 본다

**자기 점검**
- 로그에 아무것도 없이 컨테이너가 사라졌다면 무엇부터 보는가?
- 종료 코드 137 과 143 중 정상 종료에 가까운 쪽은?

## 11.3 재시작 정책과 graceful shutdown

**로우레벨의 불편함**: 죽으면 사람이 보고 다시 띄워야 한다.
반대로 `always` 로 두면 내가 멈춘 것도 PC 를 켤 때 다시 뜬다.

**해결**: 상황에 맞는 정책을 고른다.

| 값 | 동작 |
|---|---|
| `no` | 기본값. 안 살린다 |
| `on-failure` | 0 이 아닌 코드로 죽으면 살린다 |
| `always` | 항상. 내가 멈춰도 도커 재시작 시 다시 뜬다 |
| `unless-stopped` | 항상 살리되 내가 멈춘 것은 그대로 |

종료 신호를 받고 **처리 중인 요청을 끝낸 뒤** 닫도록 애플리케이션을 맞춘다.
PID 1 에서 `SIGTERM` 을 받는 것이 전제다(4.5).

**자기 점검**
- 개발 환경에 `always` 가 불편한 이유는?
- graceful shutdown 이 안 되면 사용자에게 어떤 일이 생기는가?

## 11.4 안에 들어가 보기

**로우레벨의 불편함**: 컨테이너는 최소 구성이라 디버깅 도구가 없다.
distroless 이미지에는 셸조차 없다.

**해결**: 상황별로 수단을 나눈다.

- `docker exec -it 이름 sh` — 셸이 있는 경우
- `docker logs -f`, `docker inspect`, `docker stats`, `docker top`, `docker diff`
- 셸이 없으면 **같은 namespace 에 디버그 컨테이너를 붙인다**

```bash
docker run --rm -it \
  --network container:대상 --pid container:대상 \
  nicolaka/netshoot
```

`docker diff` 는 쓰기 층에서 바뀐 파일을 보여준다. "뭘 쓰고 있나"를 찾을 때 쓴다.

**자기 점검**
- 운영 이미지에 디버깅 도구를 넣지 않는 것이 왜 맞는가?
- 셸 없는 컨테이너의 네트워크 문제를 어떻게 들여다보는가?

## 11.5 디스크를 먹는 네 가지

**로우레벨의 불편함**: 어느 날 디스크가 꽉 찬다. 뭐가 먹었는지 바로 안 보인다.

**해결**: 먹는 것은 네 가지뿐이다.

```bash
docker system df      # 종류별 사용량과 회수 가능량
docker system df -v   # 어느 이미지·볼륨이 큰지
```

| 종류 | 자주 쌓이는 이유 |
|---|---|
| 이미지 | 태그 없는 중간 이미지(`<none>`)가 쌓인다 |
| 컨테이너 | 멈춘 채 안 지워진 것 |
| 볼륨 | 컨테이너는 지웠는데 볼륨이 남는다 |
| **빌드 캐시** | 가장 조용히 커진다. 수십 GB 까지 간다 |

정리 명령은 위험도가 다르다.

| 명령 | 지우는 것 |
|---|---|
| `docker system prune` | 멈춘 컨테이너, 안 쓰는 네트워크, dangling 이미지, 빌드 캐시 |
| `prune -a` | **안 쓰는 이미지 전부.** 다음 빌드가 느려진다 |
| `prune --volumes` | **볼륨까지.** 데이터가 날아간다 |

**자기 점검**
- `docker system df` 에서 "RECLAIMABLE" 이 뜻하는 것은?
- `prune --volumes` 를 습관적으로 쓰면 안 되는 이유는?

# 📚 PART 12 — Docker Desktop (Windows · macOS)

> **목표**: 리눅스가 아닌 데서 생기는 차이를 알고, 느린 이유를 설명한다.

## 12.1 리눅스 VM 이 한 겹 더 있다

**로우레벨의 불편함**: 컨테이너는 **리눅스 커널 기능**이다.
Windows 와 macOS 에는 그 커널이 없다.

**해결**: Docker Desktop 은 **리눅스 VM 을 하나 띄우고** 그 안에서 컨테이너를 돌린다.

```
Windows/macOS
  └─ 리눅스 VM (WSL2 또는 Hypervisor)
       └─ dockerd → containerd → runc
            └─ 컨테이너
```

- "컨테이너는 VM 보다 가볍다"는 말이 **리눅스 호스트 기준**이라는 뜻이다
- Windows 컨테이너는 별개다. Windows 커널 위에서 돌고 리눅스 이미지와 섞이지 않는다

**자기 점검**
- 맥에서 컨테이너가 리눅스 호스트보다 무거운 이유는?
- Docker Desktop 을 껐을 때 `docker ps` 가 실패하는 이유를 구조로 설명하면?

## 12.2 bind mount 가 느린 이유

**로우레벨의 불편함**: 소스를 bind mount 해서 개발하면
리눅스에서는 멀쩡한데 Windows·macOS 에서는 눈에 띄게 느리다.
파일이 많은 프로젝트(`node_modules`)에서 특히 심하다.

**해결**: 경계를 넘는 횟수를 줄인다.

- 파일이 **호스트 OS 파일 시스템에 있고** 컨테이너가 VM 안에 있으면, 모든 파일 접근이 **경계를 넘는다**
- WSL2 라면 소스를 **WSL2 파일 시스템 안**(`\\wsl$\...`)에 두면 훨씬 빠르다. `/mnt/c/...` 는 느리다
- `node_modules` 같은 디렉터리는 bind 하지 말고 **볼륨으로 덮어쓴다**

**자기 점검**
- 같은 프로젝트가 리눅스에서 빠르고 맥에서 느린 이유는?
- WSL2 에서 소스를 어디에 두어야 하는가? 왜인가?

## 12.3 리소스 할당과 데몬 관리

**로우레벨의 불편함**: VM 에 할당된 CPU·메모리가 컨테이너의 상한이다.
기본값이 작으면 빌드가 느리고, 크면 호스트가 느려진다.

**해결**: 설정에서 조절하고, 안 쓸 때는 끈다.

- 메모리를 너무 작게 두면 빌드가 OOM 으로 실패한다. 원인이 Dockerfile 이 아닐 수 있다
- 디스크 이미지는 한 번 커지면 **자동으로 안 줄어든다.** 정리 후 수동 축소가 필요하다
- Docker Desktop 이 꺼져 있으면 모든 `docker` 명령이 실패한다. 가장 흔한 "안 돼요"의 원인

**자기 점검**
- 로컬 빌드만 OOM 으로 실패하고 CI 는 통과한다면 무엇을 의심하는가?
- `docker system prune` 을 했는데 디스크가 안 줄었다면 Desktop 에서 무엇을 더 해야 하는가?

# 📚 PART 13 — 단일 호스트의 한계

## 13.1 한 대로 안 되는 것들

**로우레벨의 불편함**: Compose 는 **한 호스트 안**에서만 동작한다.
